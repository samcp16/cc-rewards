## 0. 一句话结论

这是一个 **Product 寄存器的单人高频决策工具**，不是落地页。设计目标是 **"让用户在收银台前 3 秒内做出一个不需要后悔的决定"**。主查询页采用 **分区渐进披露 + 常驻实时答案**（不是分步向导，也不是一个"查询"按钮），最优方案用 **"行动指令 + 净收益大数字 + 结论句"的三行卡**呈现，多卡对比用 **统一基准的对齐数值表（含正负差值列），按净收益降序、可折叠、默认只展开前三**。

## 1. 设计寄存器与三轴刻度（先判，后设计）

### 寄存器：Product（无争议）

| 判据 | 本产品 |
|---|---|
| 路径形态 | 工具型内部界面，无 `/pricing` `/about` 营销面 |
| 用户目标 | 完成一次决策任务，不是"被说服" |
| 标杆 | Linear / Figma / Stripe Dashboard / Raycast 的熟手用户坐下来会信任 |
| 失败模式 | 装饰过度，或在每个略奇怪的控件上停顿 |

**结论：全项目 `Register: product`。** 这意味着：
- 调色板默认 **Restrained**：中性色 70–90%，强调色只用于主操作/当前选中/状态
- 字体一族 + 等宽一族即可，固定 rem 阶梯，步进比 1.125–1.2
- 动效 150–250ms，只传递状态，**无页面加载编排**
- 每个交互组件必须全状态（default/hover/focus/active/disabled/loading/error/empty/success）
- **禁止**：任何 hero 大标题、抽象图形、营销语、入场动画编排

### 平台轴：web（mobile-first，加桌面降级适配）

Phase 0 已锁"手机浏览器打开即用，可添加到桌面"。平台轴 = `web`，按 mobile-first 设计、桌面端只做加宽不加功能。

### 三轴刻度

| 轴 | 值 | 理由 |
|---|---|---|
| `DESIGN_VARIANCE` | **3** | 决策工具需要可预测的位置。用户每次都在同一位置看同一个数字，肌肉记忆是效率。Variance >4 会强制非对称布局，对这个产品是伤害 |
| `MOTION_INTENSITY` | **3** | 动效只做状态反馈（答案切换、展开对比、额度条填充）。炫耀性动效在此产品里是纯粹的干扰 |
| `VISUAL_DENSITY` | **6** | 偏高但不到"驾驶舱"。核心答案区要克制留白（3 秒可读），卡库列表与对比表要密集（一屏看多张卡） |

## 2. 联网调研：金融数据工具的界面策略

调研的产品：CardPointers、Copilot Money、Monarch Money、Linear、Stripe Dashboard、Revolut、LongPort Whale（金融终端设计系统），以及同品类的中文/繁体竞品 Cardli、PickCardRebate。

### 2.1 六条可迁移的设计策略

**① 唯一主角数字（Primary Metric Pattern）**

> "Every fintech dashboard has one number the user came to see... When you try to make five things equally important, you make nothing important."

本产品的唯一主角数字是 **本次消费的净返金额（如 `+HK$23.40`）**，不是返现率，不是卡片名称。返现率是**手段**，净返金额是**答案**。返现率作为副行右上角小字，帮助用户理解"为什么是这张卡"。

**② 语义化色彩 = 即时理解**

Copilot Money 的做法：绿=收入、红=支出、蓝=净值、黄=待处理，全产品一致。
Revolut 的做法：`semantic colors only in product`，营销面保持无色。

对本产品：**正净返、负净返（倒贴）、额度告警**需要三套语义色，且必须一致到"用户能凭颜色扫读而不读字"。见 §4.3 的正负色判断。

**③ 渐进披露（Progressive Disclosure）**

> "Progressive disclosure is arguably the single most important of all fintech dashboard design patterns, because it resolves the eternal tension between simplicity and power."

本产品的披露层级：
```
L0 常驻：最优方案（卡 + 渠道 + 净返）
L1 一步点开：Top 3 对比（默认已展开前 3）
L2 再点开：全部卡对比表（含失败原因）
L3 再点开：单卡规则明细（为什么这张卡只有 0.5%）
```

**④ 数字必须有参照点（Contextual Comparisons, Not Raw Numbers）**

> "A portfolio value of $847,293 is meaningless in isolation. Is that good? Bad? Expected?"

净返 `+HK$23.40` 本身不够，必须配 **对比基准**：`比第二名的 A 卡多 HK$12.80`。这一行是"为什么听我的"的全部说服力来源，也是这个产品能建立信任的地方。差额信息让用户不用自己做减法——这是**认知负荷转移**，是本产品最核心的价值设计。

**⑤ 状态诚实（Status and State：Honesty as a Pattern）**

> "Users tolerate delays far better than they tolerate ambiguity."

本产品最大风险不是丑，是**"推荐错了但看起来很确定"**。所以：
- 额度已用尽 → 该卡**必须被排除且明示原因**，不能静默降权
- 规则过期/未确认 → 该卡打"待确认"标记，不参与冠军排序
- 外币手续费按卡不同 → 明细里必须逐项列出，不合并成黑盒

**⑥ 密度靠结构，不靠装饰**

Monarch 2024 重设计的官方表述：`improved information density` + `boosted color contrast` + `tighter spacing`。做法是压行高、收间距、用可折叠分组，**不是加更多卡片和边框**。
Linear 的做法：`near-black background + restrained accent + zero decorative gradients`，深度靠背景层之间的细微色调台阶，不靠阴影与发光。

### 2.2 同品类竞品的关键观察（反面教材 + 正面借鉴）

我特意看了 Cardli（cardli.app）和 PickCardRebate——这是与本产品最接近的现有产品。

**他们做对的**：
- 排行榜按 **净回馈 = 回馈率 − 外币手续费** 排序（这正是本产品的核心算法）
- 每行都标出 **上限 / 门坎 / 登錄条件**——因为用户被"高回馈但月上限 300"坑过

**他们做丑了的地方（我们明确不学）**：
- 每行塞 6–8 列（回馈率、下限、月上限、手续费、净回馈、备注），一屏阅读负担极重
- 用 emoji 当分类图标（竞品实际使用了笔记本、警告、奖杯、金牌、免费五类 emoji）——**本项目 P0 禁止，见下条**
- 大段解释性文字与规则条款混排在结果区
- 冠军行靠奖杯 emoji 建立层级，而不是靠排版的字号/字重/底色

**结论**：本产品的对比表必须 **≤5 列、净返额与差值对齐、其余信息收进明细抽屉**。

### 2.3 "输入 3 个字段 → 立刻给答案"该怎么交互？

这是本次调研最关键的交互判断，我对比了三种形态：

| 形态 | 优点 | 本产品下的致命问题 | 判定 |
|---|---|---|---|
| **A. 分步向导**（步骤 1 地区 → 步骤 2 类别 → 步骤 3 金额） | 每屏一个决策，认知负荷低 | 3 步 = 3 次点击 + 2 次转场，**在收银台前是灾难**。且分步意味着"答案在第 4 屏"，违反 3 秒目标 | [否] 否决 |
| **B. 一次表单 + 查询按钮** | 实现最简单 | 多一次点击是多余的；用户改金额（把 380 改成 420）还要再点一次"查询"，打断连续性 | [否] 否决 |
| **C. 单屏分区 + **常驻实时答案**** | 0 次额外点击；改一个字段答案立刻跟着变；符合"3 秒" | 需要做好"未填完时的空状态别让人困惑" | [是] **采用** |

**为什么 C 可行**：本产品的输入天然是"离散点选"，不是长表单。地区 2 选 1、类别 6 选 1、渠道 5 选 1，都是**大按钮点选**，唯一需要键盘的是金额。用户在 3 次点击 + 1 次数字输入内完成全部输入，本身就是"一屏任务"。

**结论：单屏内联 + 实时计算（Reactive，非 Submit）。无"查询"按钮。**

交互细节：
- 所有选填字段（渠道）**预填最近一次使用值**，用户通常 0 次操作
- 金额用大号数字键盘输入，输入即计算（200ms debounce，防抖为的是不闪，不是为省性能）
- **首次使用时答案区显示"选一个类别，立刻看结果"，而不是骨架屏**——空状态即引导
- 结果切换用 <200ms 的交叉淡入，数字滚动用 tabular-nums 保证宽度不跳（防抖动是信任问题，不是美观问题）

### 2.4 "最优方案"用什么视觉形式呈现？

对比了四种候选：

| 形式 | 问题 |
|---|---|
| 大卡 + 卡面渲染图（3D 卡） | 需要品牌卡面素材，单人自用不需要；且卡面识别不靠图，靠名字 |
| 结论句大标题 | 违反 P0-5（千篇一律 hero），且在 utility 里浪费垂直空间 |
| 仪表盘式环形图/得分 | 净返不是百分比进度，环形图是错误隐喻 |
| **"行动指令 + 净收益 + 一句话论证"三行卡** | [是] 采用 |

**采用形式的精确结构**（高度约 180–200px，占首屏黄金区）：

```
┌────────────────────────────────────────────┐
│  刷这张                                     │  ← 12px 标签，meta 色，非大写英文
│                                            │
│  信银国际 大湾区双币卡                       │  ← 24px/590，fg
│  走 银联 · 人民币结算                        │  ← 14px/400，fg-2，带渠道图标
│                                            │
│  +HK$23.40                                 │  ← 40px/590，tabular-nums，正净返语义色
│  净返 2.34%   比第二名多 HK$12.80            │  ← 13px，meta 色，差值
│                                            │
│  额度还剩 HK$1,960  ▸ 已用 26%              │  ← 额度条 + 数字
├────────────────────────────────────────────┤
│  查看全部 7 张卡对比  ▾                      │  ← ghost 折叠触发器，整行 48px 触摸区
└────────────────────────────────────────────┘
```

**为什么"刷这张"这个标签而非"最优方案"**：用户的问题原话是"刷哪张"，界面回他的原话就是最直接的答案。`最优方案` 是系统的语言，`刷这张` 是人的语言。这条文案的差别是"AI 味"与"人做的"的分界。

### 2.5 多张卡对比怎么排布才不显得吵？

这是最容易做丑的地方。四条规则：

1. **统一基准**：所有卡按 **同一次消费的净返金额** 计算，可横向比较。禁止把返现率和其他卡的净返额并排（苹果比橘子）。
2. **≤4 列**：`卡名+渠道` / `回馈率` / `净返额` / `差第一名`。外币手续费不占列，收进明细行。
   - 费率与净返额的关系：费率是"因"，净返额是"果"。列顺序按用户的阅读逻辑走：谁 → 多少费率 → 落到手多少 → 差多少。
3. **正负差值用符号 + 语义色，不用只剩红色**：`−HK$12.80` 灰色（只是少赚），`−HK$4.20` 用 danger 色 + 前缀 `倒贴`（真亏钱）。**"少赚"和"亏钱"是两种情绪，必须视觉分开**，否则用户会麻木。
4. **默认只展开前 3 名**。第 4 名开始折叠（"展开其余 4 张"）。理由：单人持卡通常 5–10 张，一屏 5 行对比表的高度（约 300px）会让首屏答案被挤出可视区。
5. **失格卡不进主列表**：额度用尽/规则过期的卡在列表末尾单独一组（`不推荐 · 2 张`），带具体原因。**不能让用户以为"这张卡没算进去"**——那是信任崩塌点。

## 3. 数字的排版策略（本产品最容易翻车的地方）

这是"省钱工具"的生命线。数字排错了，产品就是玩具。

### 3.1 三级数字层级（只有三级，不搞四级）

| 级别 | 用途 | 字号/字重 | 数字格式要求 |
|---|---|---|---|
| **L-Answer** | 本次净返金额（唯一主角） | 40px / 590 | `tabular-nums`，正数强制 `+` 前缀，含币种符号 |
| **L-Stat** | 返现率、额度剩余、月度已用 | 20–24px / 510 | `tabular-nums` |
| **L-Row** | 对比表内的金额列 | 15px / 510 | `tabular-nums`，**右对齐** |

### 3.2 五条数字铁律

1. **全部 `font-variant-numeric: tabular-nums`**。等宽数字让"改金额 → 数字跳动"时宽度不变化，消除抖动。Stripe 与 LongPort Whale 的金融设计系统都把这条写成 MUST。
2. **金额列一律右对齐，标签列左对齐**。中文用户的数字阅读扫视是沿小数点/末位对齐的。
3. **币种符号缩小、金额放大**：`HK$` 用 0.7em 的 `muted` 色，`23.40` 用全尺寸 `fg`。视觉重量集中在数字上，符号只是上下文。
4. **不刺眼的三招**（关键）：
   - 深色主题下用 `#F0F6FC` 一类**带些许透明/微冷的近白**，绝不用纯 `#FFFFFF`（Copilot 用的是 90% 白，理由是"消除长时间看财务数据的对比刺眼"）
   - 大数字不用纯色满饱和的绿。用**降饱和的语义绿**（如亮度一致但 chroma 收 15%），大字号下满饱和绿会"发光刺眼"
   - 数字周围留白比文字周围多 50%。数字需要呼吸才显得"贵"
5. **小数位统一到 2 位**，不做"四舍五入到整数"。理由：一个省钱工具算错 1 块钱的可信度损失，远大于多显示两位小数的视觉成本。超过 10,000 才用千分位。

### 3.3 正负金额的展示规则（对齐"涨红跌绿"的判断）

见 §4.3。规则：
- **正净返**：数值前加 `+`，语义色 `--pos`
- **零净返**：`±0.00`，`muted` 色，副标注 `不赚不亏`
- **负净返（倒贴）**：数值前加 `−`，语义色 `--neg`，并在下方加一行 `倒贴 HK$4.20`，**明确写出"倒贴"二字**。不靠颜色单独传达（色盲 + 色彩约定歧义双重风险）

## 4. 设计方向

### 4.1 对标品牌（设计语言来源）

| 对标 | 借鉴什么 | 与本产品的契合点 |
|---|---|---|
| **Linear**（主） | 精密感与信息密度并存的证明；近黑底 + 单一克制强调色；**零装饰渐变、零发光、零层叠模糊**；深度靠背景层色调台阶而非阴影；4px 网格；Inter + 等宽点缀 | 单人、高频、工具属性。用户每天用 3–8 次，界面必须"用久了不出错"。Linear 的"精准工程感"正是这个产品该传递的气质。它证明了**密度与优雅可以共存**——这是本产品（一屏要塞下输入 + 答案 + 额度 + 对比）的刚需 |
| **Copilot Money**（次） | 深色画布让数据成为主角；**语义化色彩贯彻到底**；近白（90% 白）代替纯白减轻刺眼；品牌自己把界面描述为 "deliberately calm" | 财务数据的"平静感"。本产品用户的状态是"在收银台前，有点急，不想动脑"。界面必须让**看数字这件事降低焦虑，而不是增加焦虑** |
| **Stripe Dashboard**（校验用） | 数字可访问性体系；`tabular-nums` 作为硬规范；4.5:1 对比度体系的工程化落地 | 只用它的"工程纪律"，不用它的浅色营销面 |

**明确不借鉴**：Revolut 的商用卡面摄影与超大营销字（那是 Brand 寄存器）；Monarch 的暖色活力感（那是订阅制消费产品讨好用户的做法，本产品不需要讨好）；Cardli 的排行榜堆列（见 §2.2）。

**一句话设计语言**：**"像一台精密的仪表，不像一个 App。"** 没有欢迎语，没有插图，没有吉祥物，没有 hero。打开就是能按的按钮和能读的数字。

### 4.2 配色方向

**基调：深色为主（默认深色），提供浅色主题。**

主色决策：
- [否] 不用 Indigo `#6366F1` / 紫系（P0-2 红线 + 4.4% 的 AI 模板首罪）
- [否] 不用 Emerald 纯绿当主色（会与"正收益"语义色撞车——**主色和语义色同色是最常见的低级错误**，用户分不清"这是主按钮"还是"这是好消息"）
- [是] **主色 = 冷调近黑中性色体系**（`#0D1117` 系），强调色用**中性偏冷的蓝**（`#2563EB` 家族）作为交互色

为什么强调色是蓝而不是绿：蓝在本产品里**不承载任何金额语义**，只表示"可点击/当前选中"。这样语义色（正/负/警示）就完全清空出来给钱用。这是金融工具配色最干净的分工。

**语义色的三个槽位**（Phase 2 定具体值，此处定用途）：

| 槽位 | 用途 | 判断依据 |
|---|---|---|
| `--pos`（正净返） | 净返 > 0 的金额、收益条 | — |
| `--neg`（负净返/倒贴） | 净返 < 0，真亏钱 | 需与"少赚"区分 |
| `--warn`（警示） | 额度已用 >80%、规则待确认、即将到期 | — |

**"少赚"不配语义色**：`差第一名 −HK$12.80` 用 `muted` 灰 + `−` 符号。理由：如果所有非冠军卡都用红色差值，屏幕上会有一片红，红色失去信号价值（alarm fatigue）。**只有"真亏钱"配红。**

层级差异表达（深色模式，亮度递进而非阴影）：

```
bg        #0D1117   页面底
surface   #161B22   卡片
surface-2 #21262D   卡内分区/输入未选中
fg        #F0F6FC   主数字与标题（近白，非纯白）
fg-2      #D0D6E0   次级文本
muted     #8B949E   标签/元数据
meta      #6E7681   最弱（时间戳、"共 7 张"）
border    rgba(255,255,255,0.08)   1px 结构线
```

### 4.3 判断：要不要应用"涨红跌绿"？

**结论：不应用。本产品改用"绿正红负"。** 理由四条，逐条说清楚：

1. **约定不适用**。涨红跌绿是**股票行情**的约定，它的语义是"价格上涨/下跌"。本产品的语义是"我省到钱/我倒贴钱"——这是**收支语义**，不是**行情涨跌语义**。中国用户的收支语义约定恰恰是相反的：**支付宝年度账单里收入/结余用绿、支出用红**（这也是调研里查到的实例）。所以"绿=省钱"在中国语境下不违反任何约定，反而是对的那个。
2. **情绪方向一致**。红色在中国金融里虽然是"涨"，但它同时是**警示色**（这一点调研已确认："红色代表着愤怒和危险，并被用在警示信号和紧急按钮之上"）。用红表示"你倒贴了钱"，情绪方向是对的：倒贴是坏消息，坏消息就该是红的。
3. **红绿二分本身有缺陷**。调研明确提出交易软件已经在打破红绿二分法，改成"波动小时趋近灰色中性"，以避免数字被过度放大。本产品的做法更进一步：**"少赚"用灰，只有"亏钱"用红**（见 §4.2）。
4. **单用户产品不给切换项**。调研里对行情的建议是"提供 Western / East Asian 配色切换"。**本产品不做这个开关**——单人自用，加一个没人会用的设置项是负担。直接采用收支语义（绿正红负）并写进设计契约，用户看两次就适应，因为方向符合直觉。

**但必须做一件事**：颜色**永远不单独承担语义**。所有金额都带 `+` / `−` / `±` 符号前缀，倒贴额外带文字。这样红绿色盲用户与色彩约定分歧的用户都不会读错。这不是可选项，是硬规则。

### 4.4 字体方向

**字体配对：`Inter` + `Noto Sans SC` + 等宽一族**

```
--font-display: "Inter Display", "Inter", "Noto Sans SC", -apple-system, sans-serif
--font-body:    "Inter", "Noto Sans SC", -apple-system, sans-serif
--font-num:     "Inter", ui-monospace, "SF Mono", sans-serif   /* tabular-nums */
--font-mono:    "JetBrains Mono", ui-monospace, monospace        /* 仅用于规则代码/卡号后四位 */
```

**(a) 中文的取舍：先用系统中文，不首屏加载 Noto Sans SC**

Phase 0 已锁"手机浏览器打开即用"。而 Noto Sans SC 字体文件 ≥1MB（知识库 typography-pairings.md §22 明确提示）。一个要求"3 秒出结果"的工具，**首屏为了一个中文字形下载 1MB 是自杀**。

方案：
- **第一阶段（MVP）**：中文走系统字体栈 `-apple-system, "PingFang SC", "Microsoft YaHei", "Noto Sans SC"`。澳门/香港用户 iPhone 上是 **PingFang SC/TC**，观感本身就很好，且零加载成本
- **第二阶段（可选优化）**：若后续要品牌一致性，再做 **Noto Sans SC 子集化**（只保留用到的汉字，可压到 30–60KB）并 `font-display: swap`
- [是] 提交架构师决策项：字体加载策略属实现层，需在 Spec 里定"是否引入 webfont"（见 §9）

**(b) 数字：不引入等宽字体，用 Inter 的 `tabular-nums`**

这是本产品最重要的字体决策，也是多数人会做错的地方。**金额不要用 monospace。**

理由（调研已确认）："Monospace is necessary for code but overkill for numeric data. Tabular numerals in a proportional font give aligned columns with better readability than monospace."

Inter 的 `tnum` 特性让每个数字占等宽，列自然对齐，同时保持无衬线的可读性与紧凑性。monospace 会让金额看起来像代码，且字宽过宽浪费首屏横向空间。

实现：所有数字容器 `font-variant-numeric: tabular-nums; font-feature-settings: "tnum" 1;`

**(c) 字号阶梯（固定 rem，步进 1.125–1.2，Product 寄存器不搞 fluid clamp）**

```
--text-2xs: 0.6875rem  (11px)  仅标签/徽章，配 0.06em 字距
--text-xs:  0.75rem    (12px)  元数据、列头
--text-sm:  0.8125rem  (13px)  次级说明、差值行
--text-base:0.875rem   (14px)  正文（Product 基准，手机上 14px 才是对的）
--text-md:  1rem       (16px)  卡片名、输入值
--text-lg:  1.125rem   (18px)  区块标题
--text-xl:  1.5rem     (24px)  对比区大数字 / 额度页 KPI
--text-2xl: 2.5rem     (40px)  唯一主角：本次净返金额
```

字重三级：`400`（正文）/ `510`（数字与标签）/ `590`（卡名与主角数字）。**不引入 700**——单文件更小，且 590 在半粗区间足够有权威感而不过度。

字距：中文正文 `0`；11px 标签 `0.02em`；40px 主角数字 `-0.02em`；全大写英文（若出现，如 `HK$`）`0.06em`。

### 4.5 图标库建议（锁定一套）

**建议：`Lucide`（`lucide-react` / `lucide` SVG 包）。**

选它的理由（针对本产品）：
1. **"Lucide is particularly strong in dense interfaces because its uniform stroke weight stays legible at 16px and 20px."** 本产品要在 13–14px 的列表行里塞渠道图标（支付宝/微信/云闪付/Apple Pay/刷卡），小尺寸下的一致描边是硬需求
2. 统一 24×24 网格、2px 描边、单一风格（outline）。**本产品只需要一种图标风格**，Phosphor 的 6 字重是多余开销
3. tree-shaking 好，只打包用到的图标（包体积对小工具很重要）
4. 风格"technical / neutral / geometric"，和 Linear 的设计语言同源，与"精密仪表"的气质一致
5. ISC 许可，无署名义​​务
6. 图标覆盖满足需求：`credit-card` `wallet` `smartphone` `scan-line` `chevron-down` `plus` `pencil` `trash-2` `calendar` `arrow-up-right` `triangle-alert` `check` `x` `search` `sliders-horizontal`

**规格约束（写进设计契约）**：
- 尺寸只用三档：**16px**（行内，配 12–13px 文字）/ **20px**（按钮内、列表行）/ **24px**（底部 TabBar、空状态）
- 描边统一 `stroke-width: 2`（24 网格基准）；16px 时如需可降到 `1.75`，但**全产品只能选一个值**
- 颜色只跟随文字色（`currentColor`），**不单独给图标上色**
- **绝对禁止 emoji 作为功能图标**（P0-1）。用户自己输入的卡名/NOTE 里的 emoji 例外
- [注意] **架构师需在 Spec 中正式锁定**（我这是建议，不是终裁）

**特别提示：渠道图标（支付宝/微信/云闪付/Apple Pay）不是 UI 图标，是品牌标识。**
- 这些不能用 Lucide 画（Lucide 没有支付宝/微信图标）
- 方案 A（推荐 MVP）：**不用品牌 logo**，用 Lucide 的 `wallet` / `smartphone` / `scan-line` / `credit-card` 配合**文字标签**（`支付宝` `微信` `云闪付` `Apple Pay` `刷卡`）
- 方案 B：引入品牌 SVG（有商标风险、有额外体积、四套风格难统一）
- **明确建议方案 A**：文字标签在小屏上比 logo 更好认，且零体积、零法律风险

### 4.6 浅色 / 深色主题的判断

**结论：MVP 只做深色主题，但把 token 结构按"可扩展双主题"设计，浅色留到 Phase 2 末尾或追加需求。**

理由（这是个需要说清楚的判断，不是偷懒）：

**支持做深色的证据**：
- 本产品的使用场景包含"晚上查看本月额度、核对账单"——调研确认深色在弱光环境下明显更舒适（"晚上躺在床上看手机，黑色背景阅读白色文本要好很多"）
- 金融数据在深色画布上"数据成为主角"，Copilot Money 的整个设计论点就建立在这上面
- 深色能掩盖大量小字号数字排版的瑕疵（浅色下 11px 灰字在灰底上极易发虚）
- 手机 OLED 屏下深色省电（最高亮度可省 39–60%，30–50% 亮度省 3–14%）；一个每天开 5–10 次的工具，省电是真实的
- Google Pay / Stripe / Linear 的金融控制台默认都是深色

**为什么浅色先不做**：
- 浅色模式的对比度容差小得多。在浅色下把"正净返绿 / 倒贴红 / 少赚灰 / 警告黄"四色都做到 4.5:1 且互不混淆，工作量接近重做一套配色。**做两套半成品不如做一套精品**
- 单人自用产品，用户（本人）用两次就会形成主题预期，**主题切换的需求很弱**
- Phase 1 的目标是方向，不是穷举。省下来的精力放在"数字排版"和"对比表"这两件真正决定成败的事上

**但必须留好扩展性**：
- Token 一律写成语义名（`--bg` `--surface` `--fg` `--pos` `--neg`），实现时挂在 `:root[data-theme="dark"]` / `:root[data-theme="light"]` 下
- 一个开关就能加：`<html data-theme>`，CSS 变量整体替换
- [注意] **提交 PM 确认**：MVP 是否接受"仅深色"（见 §9 第 1 条）

**系统主题跟随**：MVP 阶段**不跟随系统**。若用户系统是浅色，我们仍然给深色（由 `data-theme="dark"` 硬设）。理由：这个产品的深色是**设计决策**（数据为主角），不是"暗色模式"。等做了浅色主题再放开跟随。

### 4.7 动效策略

**核心原则：动效只做两件事——确认状态变化，和帮助理解数字之间的关系。不做第三件事。**

| 场景 | 动效 | 时长 | 缓动 |
|---|---|---|---|
| 点选地区/类别/渠道 | 背景色 + 边框色过渡（无缩放、无弹跳） | 120ms | `ease-out` |
| **答案随输入更新** | 数字交叉淡入（旧值 80ms 出，新值 120ms 入）；卡片名更换时整体 150ms 淡入 | 200ms | `ease-out` |
| 展开/收起对比表 | 高度 + 透明度（用 `grid-template-rows: 0fr → 1fr`，**不动画 height**） | 220ms | `ease-out` |
| 额度条填充 | `transform: scaleX()` 从 0 到目标值 | 400ms | `ease-out-quart` |
| 额度超 80% | 数值与条形**变 warn 色**（颜色过渡），**不做闪烁/脉冲** | 200ms | `ease-out` |
| 展开对比时的行 | 前 3 行直接呈现；被展开的行依次 40ms 间隔淡入 | 150ms × 4 | `ease-out` |
| 保存卡片（卡库页） | 按钮内 spinner → 成功态 `check` 图标 1.5s 后回落 | 150ms | `ease-out` |

**明文禁止**（写进设计契约）：
- [否] bounce / elastic 缓动（`cubic-bezier(0.68,-0.55,0.265,1.55)`）
- [否] 任何 > 400ms 的动效（额度条 400ms 是上限）
- [否] 页面级入场编排（那是 Brand 寄存器的事，本产品禁止）
- [否] 数字"滚动计数"动画（从 0 滚到 23.40）——那是炫技，且在收银台前拖慢 3 秒目标。**直接显示终值 + 交叉淡入**
- [否] 闪烁/脉冲/呼吸灯式提醒
- [否] 同时动画 > 3 个元素
- [否] 动画 `width` / `height` / `top` / `left` / `margin` / `padding`（只动 `transform` / `opacity`）

**`prefers-reduced-motion: reduce`**：全部动效降为 0ms（包括颜色过渡），布局切换改为瞬变。这是硬要求。

**排布规则（回应"怎么不吵"）**：
1. **四列固定**：卡/渠道（flex-1）· 费率（右对齐 56px）· 净返（右对齐 72px）· 差第一（右对齐 64px）。列宽固定 → 行与行之间数字天然成列
2. **卡名 15px/510，副行 12px meta**。一级信息（卡名 + 净返）字重相同，二级（渠道/费率）压暗压小 → 眼睛扫的时候只看见两样东西

4. **默认展开 3 行，其余折叠**。理由见 §2.5
5. **失格卡独立分组**，不进排名。文案给出具体原因，不是"不可用"
6. 点任一行 → 展开该行明细（inline accordion，不是跳页）：`基础回馈 1% + 类别加码 9% = 10%;外币手续费 0%;本月加码额度剩余 HK$1,960`

## 8. 设计守则（Do / Don't）

### [是] Do

1. 答案卡永远粘在底部，拇指区，不随滚动消失
2. 所有金额 `tabular-nums` + 右对齐 + `+`/`−` 符号前缀
3. 每一屏只有一个 40px 大数字（本次净返）
4. 失格卡显式说明原因，绝不静默排除
5. 空状态就是引导（"选一个类别和金额"），不用骨架屏替代
6. 额度用"还剩多少元"表达，不只给百分比
7. 数字周围留白比其他文字多 50%
8. 一个语义只用一个颜色：主色=可交互，pos=赚，neg=倒贴，warn=将尽
9. 所有图标来自 Lucide，16/20/24px 三档，`currentColor`
10. 动效 ≤400ms，只用 `transform`/`opacity`，尊重 reduced-motion

### [否] Don't

1. [否] emoji 作功能图标（P0-1）——奖杯、警告、卡面、火焰等任何 emoji 均不得充作功能图标
2. [否] 紫→粉渐变、Indigo→Pink 任意组合（P0-2）
3. [否] "Welcome to" / "开启你的省钱之旅" / 任何营销语（P0-3）
4. [否] 首屏 hero 大标题、插图、3D 卡面、吉祥物（P0-5）
5. [否] 硬编码色值（一律走 token）
6. [否] 用 `border-left: 2px solid accent` 做卡片/行强调（AI 模板罪 #5）——用整行底色
7. [否] `background-clip: text` 渐变文字
8. [否] 装饰性毛玻璃 / 发光边框
9. [否] 所有卡都用红色差值（红会失去信号价值）
10. [否] 数字滚动计数动画（拖慢 3 秒目标）
11. [否] 卡片套卡片
12. [否] 每张卡都包一个"图标 + 标题 + 描述 + 按钮"的同构卡片（罪 #5）
13. [否] 用 emerald / 绿色做**主色**（会和"正收益"语义撞车）
14. [否] 品牌 logo（支付宝/微信/云闪付/Apple Pay 的官方标识）——用文字标签
15. [否] "查询"按钮（输入即算，没有提交动作）

## 9. 需要 PM / 架构师确认的设计前置条件

| # | 事项 | 我的建议 | 需要谁确认 | 为什么阻塞设计 |
|---|---|---|---|---|
| 1 | **主题范围**：MVP 只做深色，还是深浅双主题 | 只做深色，token 结构预留浅色 | PM | 决定 Phase 2 工作量与配色校验范围（见 §4.6） |
| 2 | **图标库锁定**：Lucide | 建议 Lucide | 架构师（在 Spec 正式锁定） | P0-1 要求 Spec 锁定一套；我这是建议不是终裁（见 §4.5） |
| 3 | **是否引入 webfont（Noto Sans SC 子集）** | MVP 先用系统 PingFang，不引 webfont | 架构师 + PM | 影响首屏体积与"3 秒"目标（见 §4.4a） |
| 4 | **"净返"的计算精度与舍入**：小数位、是否四舍五入 | 保留 2 位小数，展示层不四舍五入到整元 | PM + 后端 | 数字排版层级依赖精度定义。算错 1 元的信任损失 > 多两位的视觉成本 |
| 5 | **"额度已用"的数据来源**：纯手动录入，还是可能接账单导入 | 假设 MVP **纯手动**（单人自用，无银行对接） | PM | 若纯手动，额度页必须提供"快速更新已用金额"的入口（当前设计在编辑页）；若会导入，额度页要加"最后同步时间"和状态诚实层 |
| 6 | **"规则待确认"是否需要此状态** | 建议**MVP 不做**，用"备注"字段承载，避免多一层状态语义 | PM | 若需要，卡库/额度/对比三处都要加状态徽章，影响三类布局 |
| 7 | **渠道（刷卡/支付宝/微信/云闪付/Apple Pay）是否影响返现计算** | Phase 0 把渠道列为"可选"，但渠道实际会改变费率（很多卡 Apple Pay 有额外加码，支付宝不算外币交易） | PM + 后端 | **这是本产品最关键的逻辑前置**。若渠道参与计算，则渠道是必填而非可选，且对比表必须按"卡+渠道"组合排名，不是按卡排名。**这会改变对比表的行定义** |
| 8 | **是否显示币种换算/汇率** | 建议 MVP 不做实时汇率，MOP/HKD/USD 各自按原币种显示净返 | PM | 若要做，答案卡需要第二行换算，40px 主角数字要降级 |
| 9 | **数据持久化位置**（localStorage / IndexedDB / 后端） | 单人自用 → 设备本地即可 | 架构师 | 影响"加载失败"与"空状态"的真实形态（见 §6.1 状态表） |

**其中最需要马上确认的是第 7 条（渠道是否参与计算）**。它决定了对比表的行是"卡"还是"卡+渠道组合"，是 IA 层面的事，Phase 2 之前必须定。
