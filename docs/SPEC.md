## 1. 产品定义

**一句话**：付款前 3 秒内告诉你「这笔刷哪张卡、走哪个渠道，扣完所有手续费后净赚最多」的个人自用决策工具。

- **目标用户**：1 人。常驻中国澳门、频繁往返内地，持 8–20 张澳门/香港发卡信用卡。
- **核心问题**：无法把港澳两地的返现规则、三种计量单位（百分比/倍数/每元里数）、多层手续费放在同一把尺子上比较。
- **产品本质**：**不是信用卡管理工具，是付款前的一次性决策助手**。这条决定了下面所有功能取舍。

## 5. 核心数据模型（锁定）

> 完整定义见 `docs/ARCHITECTURE.md` §3.6。此处列出 Spec 锁定的关键结构。

```ts
export type CurrencyCode = 'MOP' | 'HKD' | 'CNY';
export type IssuerRegion = 'MO' | 'HK';           // 已移除 'US'
export type CardNetwork = 'visa' | 'mastercard' | 'unionpay' | 'amex' | 'jcb';
export type SpendCategory = 'dining' | 'grocery' | 'fuel' | 'flight' | 'hotel' | 'online' | 'other';
export type PaymentChannel = 'physical' | 'alipay' | 'wechat' | 'unionpay_qr' | 'apple_pay';
export type SpendRegion = 'MO' | 'CN';

```ts
/** 返现率：支持「本地币种 / 外币」双档（港澳卡普遍如此，38 张卡中 12 张有此结构） */
export interface CashbackRates {
  /** 本地货币签账（卡币种 == 结算币种且非跨境） */
  local: number;
  /** 外币签账（卡币种 != 结算币种，或跨境） */
  foreign?: number;       // 缺省时沿用 local
}

/** 收益轨道：排他组内取最优，组间相加 */
export interface EarnTrack {
  kind: 'cashback' | 'points' | 'unknown';
  /** cashback 用；null 表示该类别的费率为未知，禁止按 0 参与排序 */
  rates?: CashbackRates | null;
  /** points 用 */
  multiplier?: number;
  pointCurrencyId?: string;
  exclusivityGroup: string;   // 同组互斥
  capIds: string[];
  /**
   * 本轨道的渠道适用域（ADR-010）。缺省 = 全渠道适用。
   * 语义是**筛选**而非加成：不在列表内的渠道，本轨道连候选都不是，
   * 不以「值 0」形态参与排他组比较（0 会被当作「这张卡不赚钱」，而事实是「算不出来」）。
   * 全部轨道被挡 → 整卡 `channel_gated` 进 unranked，UI 须说明「换成哪个渠道可用」。
   * 约束：不得为空数组（表达「全渠道」应省略该字段），元素必须是 `PaymentChannel` 枚举值。
   */
  channelScope?: PaymentChannel[];
}
```

> **`channelScope` 与 `channelBonus`（已移除）的区别**：后者是卡级、无费率字段、`detail` 为自由文本的「渠道加成」，从未进入本 SPEC 契约，引擎零引用，无法表达「某个类别只在指定渠道是 5%」。ADR-010 已将其从 `Card` 与预置数据中删除，由 `channelScope` 承担机读语义、`note` 承担人读说明。
>
> **`channelScope` 与 `channelFees.ts` 是两个独立口径**：前者是**收益口径**（这笔算不算得出返现），后者是**手续费口径**（Apple Pay 视同实体刷卡的手续费规则）。同一个渠道可以「手续费视同实体」而「收益算不出来」，两者不冲突，不得互相引用。

> **为什么要双档费率**：渣打 Simply Cash 官方规则是「本地货币签账 1.5%，外币签账 2.0%」。港卡在澳门刷 MOP，属于外币场景，应取 2.0%；若只存单值 1.5%，结论会从「净 +0.05%」变成「净 −0.45%」，方向就是错的。38 张卡中有 12 张是这种结构，这不是个例。
>
> **谁来判定这笔交易是否走外币档**：由引擎依据 `cardCurrency` 与 `settlementCurrency` 是否相同、以及商户注册地是否跨境来决定，不由用户判断——用户看不懂这个区分，让他选只会选错。

/** 外币手续费，支持分项费率 */
export interface FxFeeRule {
  rate: number;
  splitRates?: { foreign?: number; crossBorder?: number };
  fixedFee: number;
  waivedWhen?: {
    settlementCurrencyIn?: CurrencyCode[];
    regions?: SpendRegion[];
    validUntil?: string;      // 提前 60 天警示
  };
  source: SourceRef;
}

/** 上限，支持月/年/半年 */
export interface CapDefinition {
  id: string;
  categories: SpendCategory[] | 'all';
  limitAmount: number;
  limitCurrency: CurrencyCode;
  period: 'month' | 'year' | 'half_year';
  overLimitFallback?: EarnTrack;
}

/** 优惠/豁免时效状态 */
export type ValidityState =
  | { state: 'permanent' }
  | { state: 'active'; validUntil: string; daysLeft: number }
  | { state: 'expiring_soon'; validUntil: string; daysLeft: number }  // daysLeft <= 60
  | { state: 'expired'; validUntil: string };

/** 费率溯源，UI 必须展示 */
export interface SourceRef {
  url: string;
  verifiedAt: string;   // ISO 8601
  note?: string;
}
```

**两个必须区分的时间阈值**：
- `stale_rate`：数据多久没核对 → **90 天**
- `validUntil`：优惠何时到期 → **提前 60 天警示**
- 二者是两回事，不得混用同一阈值。

## 6. 计算引擎核心算法（锁定）

### 6.1 净回报率口径

```
净回报率 = (毛返现 + 积分折算价值 − 外币手续费 − 渠道服务费) / 消费金额
排序主键 = 净回报率（不是净额）
辅助展示 = 净额（用户要看「这笔赚多少」）
```

**为什么排序用回报率**：「刷 MOP 380 赚 MOP 12」与「刷 MOP 12,000 赚 MOP 240」无法直接比较，但 3.16% vs 2.00% 可以。回报率是可比的标量。

### 6.2 执行次序（不可调换）

```
0. 判定结算路由（SettlementRoute）：由卡币种 vs 结算币种 vs 商户注册地决定
     - 'local'      卡币种 == 结算币种 且 非跨境
     - 'foreign'    卡币种 != 结算币种（含跨境且币种不同）
     - 'crossBorder' 跨境但币种相同（如港币卡在澳门以 HKD 结算）
   → 该路由同时决定：返现取哪一档费率、外币手续费取哪个费率
1. 定档（Threshold）：判断本月累计是否达到档位门槛 → 决定用哪一档费率
2. 计算毛返现：
   2a. 渠道筛选（ADR-010）：按本笔 `channel` 过滤轨道的 `channelScope`，不适用者整条移除
       （不是「按 0 计」——0 会进排他组并被取用，等于把「算不出来」渲染成「不赚钱」）；
       全部轨道被挡 → 返回 `channel_gated`，整卡进 unranked，不参与第 3 步及之后任何计算
   2b. 对剩余轨道按 exclusivityGroup 分组取最优，组间相加
3. 封顶（Cap）：按 cap.period 取对应账本周期归集，超出部分按 overLimitFallback
4. 扣外币手续费（FxFeeRule，splitRates 优先，waivedWhen 判定）
5. 扣渠道服务费（ChannelFeeRule，渠道 × 卡组织 × 金额区间）
6. 得出净回报率与净额
```

> **次序不可调换的理由**：先封顶后定档，会把高档额度错记到低档上。
> **第 0 步为新增且必须最先执行**：返现与外币手续费都依赖同一个结算路由判定，两处若各判一次，可能出现「返现按外币档、手续费按本地档」的内部矛盾。

### 6.2.1 结算路由判定表（锁定）

| 卡币种 | 结算币种 | 商户地 | 路由 | 返现取 | FTF 取 |
|---|---|---|---|---|---|
| HKD | HKD | 香港 | local | local | 通常免 |
| HKD | MOP | 澳门 | foreign | foreign | 1.95%（或豁免） |
| HKD | HKD | 澳门 | crossBorder | foreign | 按卡条款（部分免） |
| HKD | CNY | 内地 | foreign | foreign | 按卡条款 |
| MOP | MOP | 澳门 | local | local | 通常免 |
| MOP | CNY | 内地 | foreign | foreign | 按卡条款 |
| 银联双币 | CNY/MOP | 内地/澳门 | local（双币卡视同本地） | local | 0%（豁免期内） |

> 银联双币卡是特例：官方明文「以澳门币计算的款项手续费豁免」，故在港澳/内地场景按 `local` 处理且 FTF 判豁免。

### 6.3 双档净收益（解决「已用额不录入」的兜底）

每张卡同时输出两个数：

```
netRealistic  = 按账本真实已用额度计算（账本为空时等于基础档）
netOptimistic = 假设额度完全未使用（满额）
```

**UI 规则**：
- 两者相等 → 只显示一个数
- 两者不等 → **大字显示 `netRealistic`**，下方一行小字「额度用尽后降为 X」
- 用户可选择点击「记一笔」写入账本，`useLiveQuery` 自动重算

> **关键洞察**：让「记不记」不影响用户是否被误导。不记账也不会被骗，因为数字的置信度已明示。

### 6.4 不重复计算的处理

把「会不会重复」从代码里的 if 判断，变成数据里的声明：
- 每条轨道带 `exclusivityGroup`
- **同组内只取价值最高的一条**，**不同组才相加**
- 验证用例：Apple Card「Apple Pay 2% / 实体卡 1%」同组 → 只取 2%，不会得出 3%
- 渠道加成写成独立规则（不同组）→ 真叠加，符合现实语义

### 6.5 跨币种上限的处理（裁定，取代「不做汇率」的模糊地带）

**问题**：中银香港 Chill 的月上限是 **HK$150**，但主场景消费是 **MOP**。若不做任何折算，要么无法封顶，要么必须引入汇率——而 O4 明确「不建模汇率成本」。

**裁定：区分「汇率成本」与「汇率折算」。前者不做，后者必须做。**

| | 是否建模 | 理由 |
|---|---|---|
| **汇率成本**（汇兑损失、汇率波动带来的盈亏） | **不做**（O4 保持不变） | 用户明确不需要；且汇率实时变动，无法固化为可复算的数字 |
| **汇率折算**（把上限从 HKD 换算为 MOP 以便比较） | **必须做** | 不折算就算不出是否超额，上限功能直接失效。这是记账单位换算，不是成本建模 |

**实现规则**：
1. 系统内置静态折算参考表，存于 `src/domain/fx/fxReference.ts`，含 MOP↔HKD、MOP↔CNY、HKD↔CNY 三对。
2. 初始值取 **HKD 1 = MOP 1.03**（港澳市场长期稳定区间），UI **必须**显式标注：`按参考汇率 HKD 1 = MOP 1.03 折算`。
3. 该表**可由用户在设置页手动调整**（用户自己知道当前汇率）。
4. 折算**只用于上限与门槛的归集**，**不出现在「为什么」的成本项里**——它不是成本，是单位换算。
5. 凡出现跨币种折算的数字，旁边**必须有** `info` 色小字标注折算依据，**不允许静默折算**。

> **裁定意义**：不区分这两种「汇率」就会陷入两难——要么放弃上限功能（Chill 这类卡永远被高估 45%），要么违反用户「不要汇率」的要求。区分之后两个诉求同时满足。

### 6.6 数据缺口（125 个 unknown）的强制处理

卡库 38 张卡 × 7 类别 = 266 个类别字段，其中 **125 个为 `unknown`**（占 47%）。这是真实数据现状，不允许掩盖。

1. `unknown` **绝不按 0 参与排序**。0 意味着「不赚钱」，`unknown` 意味着「不知道」，两者在用户决策上完全不同。
2. 涉及 `unknown` 的卡在对比表中，数值位显示文字 **「未知」**，不是 `0.00`，也不是 `-`。
3. 若最优解来自数据不完整的卡，结论区**必须**提示「该卡此项数据待核对，结论可能偏差」。
4. 卡详情页**必须**列出该卡**具体哪些类别是 unknown**，并提供「我知道，手动填」入口。
5. 用户手动填写后 `confidence` 升级为 `user_provided`，`verifiedAt` 记为用户填写日期。

> **业务风险警示**：若 MVP 预置的 12 张卡中，用户常用类别的 `unknown` 比例过高，产品会在最关键场景上给不出答案。**Phase 3 开始前，架构师必须对预置 12 张卡的 7 类别做一次缺口复盘**，必要时缩小预置范围以确保「常用类别不空」。

## 11. 内嵌已知坑（从调研与记忆拉取）

| 坑 | 技术栈指纹 | 根因 | 修法 |
|---|---|---|---|
| iOS Safari 清除 7 天未交互站点的 IndexedDB | pwa / safari | 平台策略，非 bug | 强制安装引导 + `storage.persist()` + 导出备份 + 静默清空检测（F11） |
| 港卡 FTF 默认 0% 导致系统性高估 1.95% | 数据模型 | 第三方汇总站旧值 | 按 `issuerRegion + network` 二维带出，逐条带官方来源 |
| 单一 `rate` 存不下 BCM 的外币/跨域分项费率 | 数据模型 | 建模粒度不足 | `FxFeeRule.splitRates` |
| 上限按自然月归集会算错按年上限的卡 | 数据模型 | `period` 只有 `'month'` | 扩为 `month / year / half_year`，账本同时写 `monthKey` 与 `yearKey` |
| 等到优惠过期才报错，用户已按错误答案消费 | 时效模型 | 只判「是否过期」不判「即将过期」 | `ValidityState.expiring_soon`，提前 60 天警示 |
| `unknown` 数据被当 0 参与排序，静默给出错误推荐 | 计算引擎 | 默认值填充 | `unknown` 不参与排序 + 结论区显式提示 |
| 优惠豁免期到期后仍按 0 计算 | 计算引擎 | `validUntil` 未进计算 | 引擎判定 `ValidityState` 后再决定豁免是否生效 |
| 用 emoji 当 UI 图标 | 前端 | 默认习惯 | ESLint 规则 + CI grep 门禁，图标只用 lucide-react |
| 硬编码颜色绕过 Token | 前端 | 图省事 | `@theme` + ESLint `no-restricted-syntax` + CI grep 双门禁 |
