# ADR-005: 月度上限账本 —— 默认不记 + 双档净收益

## Status

Accepted (2026-10-31)。本 ADR 记录本项目最重要的一个设计决策，直接决定产品可信度。

## Background

信用卡返现多有月度上限（如「餐饮 4x 积分，每月上限 5000 美元」）。用户会多次使用本工具：先在超市刷了一笔，30 分钟后又想知道餐厅刷哪张卡。

**问题的本质**：月度上限是跨查询的状态。要算准，工具必须知道「本月已用额度」。而工具无法自动知道——它不在支付链路里。

三个候选：

| 方案 | 机制 | 上限准确度 | 用户成本 | 评价 |
|---|---|---|---|---|
| A. 不记录 | 每次都按"额度满额"算 | 0 分，越用越离谱 | 0 | 淘汰：上限形同虚设，会给用户虚高收益去刷错卡 |
| B. 强制记录 | 每查一笔必须先确认已刷才出结果 | 100 分 | 每笔多 1-2 步 | 淘汰：直接违反"3 秒出结果"这个最在意的点 |
| C. 默认不记 + 一键记账 + 双档净收益 | 出结果时同时给"额度充足"与"额度已用"两档；用户刷完点「记下」写账本 | 愿记则 100 分，不记也不误导 | 0 或 1 次点击 | **选中** |

关键约束：自动记账**不可行**。工具不知道用户是否真刷了、刷了多少（可能付失败、可能金额不同、可能换卡）。自动记账会造成账本污染——比不准更糟。

## Decision

采用**方案 C：默认不记账，一键记账，每张卡输出双档净收益。**

### 1. 双档净收益

每个候选方案输出两个数：

- `netOptimistic`：假设该卡对应额度池完全没用过
- `netRealistic`：按账本真实已用额度计算

展示规则：

- 两者相等 → 只显示一个数（绝大多数情况）
- 两者不等 → 显示 `netRealistic` 为大字，下方小字 `额度用尽后降为 X`

这样无论用户记不记账，**他看到的主数字都是按已知信息能给出的最诚实估计**，且他清楚这个数字的置信度（通过小字）。

### 2. 账本条目

```ts
interface LedgerEntry {
  id: string;
  cardId: string;
  occurredAt: string;      // 用户可改，支持补记
  periodKey: string;       // 'YYYY-MM'，由 occurredAt 派生
  amount: number;
  currency: CurrencyCode;
  category: SpendCategory;
  channel: PaymentChannel;
  capConsumption: Record<string, number>;  // capId -> 本笔消耗额
  earnedCashback: number;
  earnedPoints: number;
  note?: string;
  createdAt: string;
}
```

### 3. 上限池抽象（CapPool）

上限不一定按卡，可能按「卡 + 类别组合」共享。构造 `capId = ${cardId}:${capGroupKey}`：

- `'dining'` — 仅餐饮
- `'all'` — 全类别共享
- `'dining+grocery'` — 餐饮与超市共享同一池

一条规则可引用 0..n 个 cap。归集时按 `capId` 累加。

一个轨道若挂多个 cap，取**剩余额度最少者**作为约束（木桶原理）——因为必须同时满足所有上限。

### 4. 周期

`periodKey = 'YYYY-MM'`，按**自然月**，不按账单周期。

理由：各卡账单日不同，建模成本高；用户自查时也按自然月想"这个月还剩多少"；精度损失可接受且 UI 明示。

### 5. 可改错

账本列表页支持编辑 / 删除。删除后 `useLiveQuery` 自动重算，上限立即回滚。这是方案 C 成立的**必要条件**——错了必须能改，否则账本会永久污染。

## Consequences

### 正面

- 不牺牲"3 秒出结果"：不记账时零额外操作
- 不欺骗用户：主数字永远基于已知信息，且能看到额度用尽后的降级值
- 账本可控：用户完全掌握写与不写、写错可改
- 上限池模型可表达真实世界的"共享额度"场景（如全类别共享）

### 负面

- 用户不记账时上限仍不准。但这是**显式的不准**（有降级提示），不是静默错误。产品诚实告知，用户自己决定要不要记
- 自然月与账单周期不对齐，月末月初可能偏差
- 上限币种与消费币种不一致时不精确（不做汇率换算，按 1:1 保守估算并警告）——见 ARCHITECTURE §6.2
- 需要额外的账本管理 UI（LedgerPage + 编辑/删除），约 1 人日

### 不做什么

- 不做自动记账（会造成账本污染）
- 不做账单周期对齐
- 不做跨币种上限精确换算（需联网查汇率，破坏离线与隐私）
- 不做"满 3 笔返 50"这类序列依赖活动的额度追踪
