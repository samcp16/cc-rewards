# ADR-013: 安装引导按平台分叉（iOS 给步骤，安卓给真按钮）

## Status
Accepted (2026-11-01)

## Background

安装引导（F11）原本按纯 iOS 视角实现：弹窗标题「装到主屏幕，卡库才不会丢」，
四步全是「点屏幕底部的分享按钮」→「选添加到主屏幕」。这段逻辑源自一个真实的
P0 风险：iOS Safari 对未「添加到主屏幕」的站点，7 天未交互即清除 IndexedDB，
用户辛苦录入的卡库会静默消失。安卓没有这个清除机制。

问题在两处暴露：

1. **注释与实现不符**。`installGuide.ts` 与 `useInstallPrompt.ts` 都写着
   「Android 走 beforeinstallprompt 原生走安装条」，但 `grep beforeinstallprompt src/`
   只匹配到这两处注释，**零实现代码**。也就是说安卓用户点「安装到桌面」时，
   `canPromptInstall()` 永远为 false。
2. **安卓用户拿到无法执行的说明**。安卓上没有「底部分享按钮」，用户在 Chrome 里
   照着做找不到入口，合理结论是「这产品坏了」。

## Decision

安装引导按平台分叉，两个平台给**结构性不同**的方案，不是同一段文案换措辞：

| | iOS | 安卓 |
|---|---|---|
| 能力 | 网页无法触发「添加到主屏幕」 | `beforeinstallprompt` 可存事件、由手势触发原生安装框 |
| 方案 | 4 步操作引导，把用户送到系统 UI | 真按钮「安装到桌面」，一键触发 |
| 兜底 | 非 Safari 时提示「先换用 Safari」 | 无事件时（微信内置浏览器等）给 3 步菜单引导 |

配套的接线约束（缺一条整个功能就是死的）：

- `initInstallPrompt()` **必须在应用入口 `main.tsx` 调用**。事件只在满足安装条件时
  触发一次，放在组件里监听等于永远收不到 —— 用户点开设置页时事件早就发过了。
- 事件到达时 `preventDefault()`，**不自动弹框**。Chrome 默认会弹迷你信息条，
  那在用户眼里就是广告；而设置页是他主动找「怎么装」的地方，在那里给按钮
  接受率更高。
- `prompt()` 必须在用户手势（click）里调用，且**一个事件只能用一次**，
  无论用户接受还是拒绝都要清空 `deferredPrompt`。
- `appinstalled` 后清空事件，不再给按钮。

安卓**不自动弹**引导（`shouldConsiderInstallGuide` 仍只对 iOS 返回 true）。
理由：安卓有原生安装能力，也没有 7 天清除风险，弹窗只会打断「3 秒看到答案」
这个核心体验。入口放在设置页，用户主动找得到就够。

## Consequences

正面：
- 安卓用户从「照着 iOS 说明找不到按钮」变成「点一下装好」。
- 一段只存在于注释里的承诺变成真实代码，且被 12 个用例锁住事件生命周期
  （其中 5 个通过变异测试验证过真实拦截能力：删 `preventDefault`、把 init 改成
  空实现、prompt 后不清空事件，全部被捕获）。
- 「宁可不给按钮，也不给假按钮」这条原则被写进代码而非仅存于注释。

负面 / 代价：
- 两个分支意味着两套文案与两套兜底，后续改文案必须两边都看。
- `beforeinstallprompt` 是 Chromium 私有事件，Firefox for Android 不派发，
  这类用户会走 3 步手动兜底（可接受，但仍需手动）。
- headless Chromium 不派发该事件，自动化测试必须注入才能覆盖一键安装路径；
  真实的「安装框弹出」无法在 CI 里断言，只能验证到 `prompt()` 被调用。
