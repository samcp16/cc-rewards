# ADR-007: 核心指标采用净回报率口径，渠道服务费为一等扣减项，门槛与上限分别建模

## Status

Accepted (2026-10-31)

## Background

本项目的架构骨架初稿把核心输出定义为「净收益金额」，并把外币手续费作为唯一扣减项。与 `docs/PRD.md` v1.0 对账后，发现两处必须修正：

### 1. PRD 定义的交付物是「净回报率」，不是「净收益金额」

PRD §4.3 明确：产品的核心交付物不是「推荐一张卡」，而是「一张扣完所有成本的可比净回报率排名」。

```
净回报率 = (返现额 + 积分折算价值 − 外币手续费 − 渠道服务费) ÷ 消费金额
```

为什么这个差异重要：用户在不同金额下要能横向比较。"刷 MOP 380 赚 MOP 12"和"刷 MOP 12,000 赚 MOP 240"无法直接比较哪个更划算，而 3.16% vs 2.00% 可以。回报率是**可比的标量**，金额不是。

### 2. 渠道服务费与外币手续费同量级，不能只做展示层提示

PRD D2 与 F1-AC2 要求渠道服务费**参与排序**，不得仅在展示层提示。已核实其量级：

| 场景 | 渠道服务费 | 来源（核实日期 2026-10-31） |
|---|---|---|
| AlipayHK + Visa/MC，月内 HKD 3,000 以上部分 | 2.5% | alipayhk.com FAQ |
| 跨境钱包链港卡（AlipayHK / WeChat Pay HK） | 1.5%–2% | comparecard.hk《電子錢包綁定攻略 2026》 |
| 内地微信/支付宝直绑境外 Visa/MC，200 元以上 | 3% | longbridge.com；evision.news |
| 云闪付绑港银联卡 | 0% | 同上 |

对比外币手续费（美国卡 3%、香港卡 1.95%），渠道服务费**同一量级**。两者叠加时，一张"餐饮 3% 返现"的香港卡走内地支付宝，净回报率可能是负的——这正是产品最该讲清楚的事。

### 3. 门槛与上限是相反方向的约束，不能用同一套模型

| | 上限 Cap | 门槛 Threshold |
|---|---|---|
| 语义 | 用得多 → 收益**减少** | 用得多 → 收益**增加** |
| PRD 例 | 美国卡季度 5x 上限 $1,500 | 澳门卡当月累计 MOP 15,000 后餐饮自 1.5% 升至 3% |

PRD F5 明确要求两者都建模。初稿只有 Cap，遗漏 Threshold。

## Decision

### 1. 输出口径改为净回报率

`Scheme` 增加 `netRateRealistic` / `netRateOptimistic`（百分比），排序**主键改为净回报率**，净额作为辅助展示。

金额字段继续保留（用户要看"这笔赚多少"），但**排序依据是回报率**。

### 2. 渠道服务费进入计算主链路

新增 `ChannelFeeRule`，建模为「渠道 × 卡组织 × 金额区间」的三维函数（不是常数）。与外币手续费共用同一套"查表优先级"（卡级覆盖 > 三元组匹配 > 兜底）与同一套"月度免费额度走账本"机制。

`SchemeBreakdownItem.kind` 增加 `'channel_fee'`，满足 F4-AC1「必须至少包含四项：毛返现、外币手续费、渠道服务费、净额」。

### 3. 门槛独立建模，且计算次序固定为「先定档、再封顶」

新增 `ThresholdDefinition` / `ThresholdTier`。引擎执行次序：

```
规则激活 → 门槛定档（选中最高的满足档）→ 应用该档的 earn → 上限扣减 → 汇总
```

次序不可颠倒。若先封顶再定档，会把本应按高档消耗的额度错记到低档，导致上限消耗计算错误。

### 4. 账本增加季度口径

`LedgerEntry.periodKey`（`YYYY-MM`）+ `quarterKey`（`YYYY-Qn`）双写。归集时按 cap / threshold 各自的 `period` 选对应 key。

### 5. 冠亚军「基本持平」判定

排序完成后，若 `schemes[0].netRateRealistic − schemes[1].netRateRealistic < 0.1`（百分点），给前两名都打 `tieWithNext` 标记。对齐 F1-AC4。

这不是 UI 细节，是产品诚信底线：差额过小时给出"唯一正确答案"是误导。

## Consequences

### 正面

- 用户得到的是**可比标量**，可在任意金额下横向比较
- 渠道费进入排序后，能正确呈现"高返现卡叠加高渠道费后反而亏"这一产品核心洞察
- 门槛建模覆盖澳门卡的典型结构（月签门槛升档），这是三地规则差异中最容易被算错的一类
- 每项扣减可独立溯源，`breakdown` 直接满足 F4 的可解释性要求

### 负面

- 计算引擎复杂度上升：三条扣减链路（外币手续费、渠道服务费、固定费）+ 两条约束链路（门槛、上限）交叉
  - 缓解：每条链路独立成文件（`resolveFxFee.ts` / `resolveChannelFee.ts` / `applyThreshold.ts` / `applyCap.ts`），各自 <200 行，各自独立单元测试
- 测试面变大：需要覆盖「门槛已达 + 上限已满」的组合场景（这是最容易出沉默逻辑错误的地方）
- `Scheme` 字段增加，前端渲染逻辑相应变复杂

### 不做什么

- 不做汇率换算（Phase 0 锁定）
- 不做 DCC 加点建模（改为警示）
- 不做季度轮换类别的自动激活（P1，且需用户手动维护）
