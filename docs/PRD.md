## 0. 一句话定位与目标用户

> **付款前 3 秒内告诉你「这笔刷哪张卡、走哪个渠道，扣完所有手续费后净赚最多」的个人自用决策工具——不记账、不理财、不连银行。**

- **主用户（唯一用户）**：1 人。常驻中国澳门 / 往返内地的个人持卡人，同时持有澳门发卡、香港发卡、美国发卡三类信用卡（预估 8–20 张），对返现有认知但记不住几十条规则，愿意一次性花 30–60 分钟把自己的卡录进去，之后每次付款只想「输入金额 + 选类别 + 看结论」。
- **技术水平**：非开发者。会用手机浏览器 / 微信内打开网页，不装复杂软件，不接受扫码登录、不接受授权银行账户。
- **反画像（明确不服务）**：多人团队、需要报销对账的人、想追踪授信额度与还款日的人、想攒里数兑换机票的人、需要税务凭证的人。

**产品本质不是「信用卡管理」，是「付款前的一次性决策助手」。** 这两者的功能集几乎不重叠——这是本 PRD 最重要的一句判断，第 12 节所有砍功能决策都由它推导。

## 1. 问题陈述

**谁 / 什么场景 / 现在怎么办 / 为什么不行**

用户在澳门（或内地）餐厅结账、超市买单、网上付款前，面对钱包里 10+ 张分属三地发卡的信用卡，需要在几秒内判断：这笔该用哪张？

现在的做法及其失效原因：

| 现状做法 | 为什么不行 |
|---|---|
| 凭记忆 | 三地规则互相干扰：美国卡「餐饮 4x」、香港卡「HK$4=1 里」、澳门卡「本地餐饮 1.5%，月签 MOP15,000 才升 3%」——三种单位（倍数 / 每元里数 / 百分比）在同一个人脑里无法横向比较 |
| 翻银行 App / 权益页 | 一家银行一个 App，且权益页只讲「本卡多好」，从不讲「比别的卡差多少」；澳门中小型发卡行甚至没有权益查询入口 |
| 翻小红书 / 论坛经验帖 | 帖子按「卡」组织，不按「我的场景」组织；且写帖人所在地区、货币、消费习惯与用户不同，结论直接套用会亏钱 |
| Excel 手工表 | 维护成本压垮一切：一次权益调整就要改一行公式，改完还得自己重算；用户在 FiCo 论坛与 Reddit 的原始表述是「每天 5–10 分钟盯表」——对一次性决策工具而言这是负价值（见 §3 来源 S6/S7） |
| 直接问 AI 聊天 | 需要把 10 张卡的规则每次重新描述一遍，且对「澳门发卡 / 香港发卡 / 美国发卡在同一笔 MOP 消费上分别触发什么」这类跨区规则极易给出看似合理实则错误的答案，且答案不可复算、不可追责 |

**核心痛点不是「不知道有哪些优惠」，而是「无法把三地、三种计量单位、多层手续费约束放在同一把尺子上比较」。** 现有工具没有一把这样的尺子——这是市场空白所在（§4 有独立论证）。

## 2. 用户核心任务流（Task Flow，点击级）

主流程目标：**从打开到看到结论 ≤ 3 次点击 + 1 次金额输入 + 1 次类别选择。**

### 2.1 T1 首次建库（Onboarding，一次性）

```
[打开链接]
  → A1 落地屏：直接是「算一笔」主界面（无欢迎页、无注册、无引导轮播）
      · 顶部一行说明文案：「先添加你的卡，之后每次付款只看结论」
      · 主区一个按钮「添加我的第一张卡」+ 一个弱化的「先试用（用示例卡）」
  → A2 点击「添加我的第一张卡」→ 进入模板选择屏
      · 搜索框（输入卡名关键词，如「AmEx Gold」「渣打 Cathay」「大豐 Visa Infinite」）
      · 模板列表每行：卡名 / 发卡地区标签 / 币种 / 主类别返现率摘要
      · 底部「没有我的卡，手动创建空白卡」
  → A3 点击某个模板 → 进入「规则确认屏」（预填写好的可编辑表单）
      · 必填已预填：发卡地区、结算币种、外币手续费率、通用返现率
      · 已预填且可改：7 个消费类别的返现率
      · 可选填：月度/季度上限、月度累计门槛（如「月签 MOP15,000 后餐饮升至 3%」）
      · 已预填但默认关闭：季度轮换类别开关
  → A4 点击「保存这张卡」→ 回到 A2，卡片出现在已添加列表顶部
      · Toast 提示「已添加，可继续添加下一张」+ 保留在 A2 列表页
  → A5 重复 A2–A4 直到卡片录完 → 点击顶部「开始算」→ 回到 A1 主界面
```

**已内嵌的坑（架构师与设计师必读）**：
- **坑 1**：不要在 Onboarding 里做「向导式 5 步注册流程」。用户只有 1 人，向导是给陌生人设计的。A2/A3 必须允许随时退出与随时回来，中途退出不得丢数据。
- **坑 2**：模板值必须是「可以让用户看不懂但可以照抄」的形态。例如香港卡的「HK$4 = 1 Asia Miles」不能直接给用户填「2%」——表单里必须同时显示原始单位与折算后的等效返现率，用户改原始单位、折算值自动更新（详见 §7 F2 与 §13 开放问题 Q1）。
- **坑 3**：A3 保存时不允许空着「外币手续费率」保存。该字段默认值必须按 `发卡地区 + 卡组织` 二维自动带出（详见 F2-AC3），因为这是全产品最高频算错的字段。

### 2.2 T2 付款前算一笔（核心主链路，日常最高频）

```
[A1 主界面]
  → B1 输入金额（数字键盘直接唤起，光标已聚焦，无需点击输入框）
      · 默认币种按当前选择地区自动带出（澳门 → MOP，内地 → CNY），可一键切换
  → B2 点选消费类别（7 个横向 chip：餐饮 / 超市 / 加油 / 机票 / 酒店 / 网购 / 其他）
      · 默认高亮上次选择的类别（记忆上次选择，减少一次点击）
  → B3 点选支付渠道（5 个 chip：刷卡 / 支付宝 / 微信 / 云闪付 / Apple Pay）
      · 默认高亮上次选择的渠道
  → C1 结果区实时出现（不需要点「计算」按钮，输入即算）
      · 第一位：冠军卡，大字号显示「净回报 X.XX%」+「净赚约 MOP 12.30」
      · 第二位起：按净回报降序的完整排名（每行一条），显示净回报率与净赚金额
      · 每行右侧一个「为什么」图标（放大镜图标），点开显示该行的算式分解（见 C2）
  → C2 点击任意一行的「为什么」→ 底部抽屉展开算式
      · 逐行列出：毛返现 + 积分价值 → 减外币手续费 → 减渠道服务费 → 净额
      · 若该卡因上限封顶或未达门槛而被打折，抽屉顶部必须显式提示（如「本月餐饮类已达上限 MOP 300，按基础 0.5% 计」）
      · 抽屉关闭按钮 + 点遮罩关闭
  → 结束：用户看完冠军卡即离开（不需要「确认」「保存」「记账」任何动作）
```

**点击预算核对**：输入金额（0 次点击，直接打字）+ 选类别（1 次）+ 选渠道（1 次）= **2 次点击**，优于 3 次的目标。若用户接受默认类别与默认渠道，则为 **0 次点击**。

**已内嵌的坑**：
- **坑 4**：结果必须「输入即算」，不允许有「计算」按钮。任何额外的一次点击都在侵蚀「用得爽」这条第一优先级。
- **坑 5**：冠军卡与第二名若净回报差 < 0.1 个百分点，必须在 UI 上标为「基本持平」，并给出次级建议（如「用这张能更快达成香港卡的每月签账门槛」）。**差额过小时给出「唯一正确答案」是误导**，这条是产品诚信底线。
- **坑 6**：净回报为负数时必须显式显示负数（红色），不得截断为 0 或隐藏。用户需要知道「这笔刷这张是亏的」，这正是本产品相对银行 App 的核心价值。

### 2.3 T3 维护卡库（低频，权益变动时）

```
[A1 主界面] → 顶部「我的卡」入口（卡片堆叠图标）
  → D1 卡库列表：每行 卡名 / 发卡地区 / 结算币种 / 主要返现率 / 右侧「编辑」「停用」
  → D2 点击「编辑」→ 进入与 A3 相同的规则表单（同一组件，不新建页面）
      · 表单顶部显示「上次修改：2026-03-12」
  → D3 修改后「保存」→ 回到 D1，主界面结果立即用新规则重算（无需刷新）
  → D4 点「停用」→ 二次确认「停用后不再参与比较，历史数据保留」→ 确认为软删除
```

### 2.4 T4 活动叠加（P1，MVP 不含）

```
[C1 结果区] → 点击某卡行的「叠加活动」图标
  → E1 抽屉内：列出该卡当前启用的活动（描述 / 加码率 / 有效期 / 适用类别 / 适用渠道）
  → E2 「添加一个活动」表单：活动名 / 加码率 / 起止日期 / 适用类别 / 适用渠道 / 上限
  → E3 保存后，若当前这笔命中该活动，C1 中该卡净回报立即重算并标注「含活动」
```

## 4. 市场空白结论（核心洞察）

### 4.1 同类工具普遍死在哪？——三个死因，按致命程度排序

**死因一：数据维护成本（最致命，且无解的具体形态）**

所有返现决策工具的价值 = `决策准确度 × 卡库覆盖度 ÷ 用户维护成本`。三者中前两项竞品都做到了 80 分，唯独第三项是**结构性负债**：

- CardPointers 靠「免登录、只填卡名、官方维护卡库」把维护成本降到最低——但它只对**美/加卡**成立，因为这些卡有公开、结构化、可批量抓取的规则。**澳门发卡与香港发卡不具备这个条件**：澳门发卡行多为中银信用卡（国际）等机构在澳门地区发行，规则以中文 PDF 条款承载、且大量规则挂在「推广期 2025-01-01 至 12-31」这种年度期限上，无统一数据源。
- 想抄 CardPointers 的「官方维护卡库」路线 → 需要持续维护澳门+香港+美国三地数千张卡的中文条款解析，这是**一个人做不完、一个人也不需要做全**的事。
- **结论：不要把维护成本转移到「做一个全卡库」上。反过来利用单人自用的特点——用户只有 10–20 张卡，而且用户本人就是唯一的数据源和唯一的数据消费者。** 让用户花一次性 30–60 分钟录入自己的卡，然后永久复用。这就是 Phase 0 已锁定的「自助增删改 + 模板一键带出」的真正理由，不是「省事」，而是**这是本场景下唯一可持续的数据模型**。

**死因二：规则过期与信息腐烂（静默失败）**

返现规则是**高频率、无通知、无版本号**变动的对象。三地尤甚：澳门卡的返现几乎全部挂在年度推广条款下（每年 1 月重新发一次 PDF），香港卡的里数兑换比率与月签门槛几乎每季度调整，美国卡的季度轮换类别每 3 个月一换。

- 竞品的失败形态是「**静默错误**」：规则变了但库里没变，用户照旧被推荐，直到某天发现返现不对——**信任一次性崩塌，且无法修复**。
- 这个坑对单人自用产品的正确解法不是「自动同步」（做不到），而是：**每张卡显示「上次确认日期」，并在结果区对该卡显示数据新鲜度标记**。当数据超过 N 天未确认时，冠军卡旁边出现「规则可能已变，确认一下」的提示。产品明确承认自己不保证数据新鲜——**承认不完美比假装完美更能建立长期信任**（见 §7 F6）。

**死因三：录入太麻烦 / 要求授权过重**

MaxRewards 的差评把这条演绎得最彻底：为了自动化，它选择绑定银行账号；绑定引发安全不适；安全不适导致用户解绑；解绑后 App 直接「pretty useless」；再叠加同步断连，最终用户卸载。**自动化能力越强，前置授权越重， abandonment 越高。**

- 单人自用场景的判断：**任何形式的账号绑定、银行授权、短信验证、登录注册，一律不做。** 理由不是「做不了」，而是「做了就把用户从 1 步决策变成 N 步授权，与『用得爽』直接冲突」。数据存在用户本地（见 §13 Q4），产品本身不拥有任何用户资产，也就不需要保护任何用户资产。

### 4.2 单人自用场景下，最小可用的产品边界在哪？

**判据（本 PRD 用于裁剪所有功能的一句话规则）：**

> **一个功能进入 MVP，必须能改变「付款前那一秒的推荐结果」或「让用户更快拿到这个结果」。若它只是让工具更像一个「信用卡管理系统」，一律砍掉。**

| 看起来有用、实际不用（明确不做，详见 §9） | 为什么看似有用 | 为什么实际不用（单人自用） |
|---|---|---|
| 账单导入 / 消费流水 / 支出报表 | 「能自动知道我花了多少、离上限还有多远」 | 需要邮箱解析或银行授权（= MaxRewards 的死因）；单人自用下用户自己心里有数；**且它改变不了「这笔刷哪张」**，只在「上限还剩多少」这一个子问题上帮忙——该子问题用「手动填一次本月已用额」即可解决（P1 即可） |
| 授信额度 / 还款日 / 免息期管理 | 「一站式」 | 云闪付已做得极好且免费；与本产品核心任务零交集 |
| 开卡奖励（SUB）追踪 | 竞品标配 | 单人自用且卡已持有，SUB 是「申请时」的决策，不是「付款时」的决策 |
| 里程/积分余额追踪与兑换搜索 | 竞品标配 | PointsYeah 专做此事且更强；本产品只需「每里值多少钱」这一个标量输入 |
| 卡面美化 / 主题 / 多套配色 | 提升愉悦感 | 「用得爽」指的是决策快，不是好看；不改变推荐结果。（注：视觉质量仍然要达标，但不做「卡面管理」这类功能） |
| 社交分享 / 推荐给朋友 / 邀请 | 增长 | 单人自用，无增长目标 |
| 多用户 / 家庭账户 / 权限 | 竞品标配 | Phase 0 已锁：仅个人自用 |
| 汇率成本建模 / 实时汇率 | 「更精确」 | Phase 0 已锁：不建模汇率成本；且实时汇率引入外部依赖与失败面，收益远小于「外币手续费 + 渠道服务费」这两项真实可算的成本 |
| 云端同步 / 账号体系 | 「换设备不丢」 | 单人自用，1–2 台设备；用本地存储 + 导出/导入 JSON 覆盖即可（见 §13 Q4） |
| AI 自动识别小票 / 拍照记账 | 「很酷」 | 与本产品决策点无关；且引入识别失败分支，拉低「3 秒」核心指标 |

**结论：MVP 的最小可用边界 = 一张「我的卡规则表」+ 一个「输入即算」的比较器 + 一个「为什么」算式展开。** 三者之外全部是 Backlog。

### 4.3 「外币手续费吃掉返现」有多重要？——这是产品的价值支点，不是边角料

**这是本产品最该讲清楚的一件事，也是它相对所有竞品的独特卖点。** 以下算式均按「MOP 1,000 餐饮消费」实算（算式与结论可复核，计算脚本见 §14 端到端验证）。

| 场景 | 毛返现 | 外币手续费 FTF | 渠道服务费 | **净额** | **净回报率** | 结论 |
|---|---|---|---|---|---|---|
| AmEx Gold（美国发卡，餐饮 4x，积分按 1.5 分/点估值，**无 FTF**） | +MOP 60.00 | 0 | 0 | **+60.00** | **+6.00%** | 最优 |
| CapOne Savor（美国发卡，餐饮 3%，**无 FTF**） | +MOP 30.00 | 0 | 0 | **+30.00** | **+3.00%** | 优 |
| Citi Custom Cash（美国发卡，餐饮 5%，**FTF 3%**） | +MOP 50.00 | −30.00 | 0 | **+20.00** | **+2.00%** | **5% 的名义返现只剩 2%** |
| AmEx BCE（美国发卡，餐饮 3%，**FTF 3%**） | +MOP 30.00 | −30.00 | 0 | **0.00** | **0.00%** | **返现被手续费 100% 吃掉，白刷** |
| Chase Freedom Unlimited（美国发卡，餐饮约 1.5%，**FTF 3%**） | +MOP 15.00 | −30.00 | 0 | **−15.00** | **−1.50%** | **越刷越亏** |
| AmEx Gold 经**支付宝/微信**付内地餐饮（>CNY 200，平台服务费 3%） | +MOP 60.00 | 0 | −30.00 | **+30.00** | **+3.00%** | **同一张卡，换渠道净收益腰斩（6% → 3%）** |
| Chase Freedom Flex 经支付宝付内地餐饮（FTF 3% + 平台 3% 叠加） | +MOP 15.00 | −30.00 | −30.00 | **−45.00** | **−4.50%** | **双重收费叠加，最差** |
| 澳门大丰 Visa Infinite 本地餐饮（未达月签 MOP15,000，仅 1.5%） | +MOP 15.00 | 0 | 0 | **+15.00** | **+1.50%** | 基准 |
| 澳门大丰 Visa Infinite 本地餐饮（已达月签 MOP15,000，升 3%） | +MOP 30.00 | 0 | 0 | **+30.00** | **+3.00%** | 门槛触发后翻倍 |
| 澳门大丰卡 内地餐饮**线上**（条款明确排除线上餐饮，仅 1x 积分） | +MOP 2.50 | 0 | −30.00 | **−27.50** | **−2.75%** | **同是「餐饮 3% 的卡」，落到线上场景直接变亏损** |

**三条足以支撑产品立项的结论：**

1. **「3% FTF 会抹掉 3% 及以下的全部返现」是硬事实**（表格第 4、5 行）。口语化的「我有张 3% 餐饮的卡」，在澳门餐饮场景下真实收益是 **0% 或 −1.5%**。**这是任何银行 App、任何比较平台、任何经验帖都不会主动告诉用户的一句话。**
2. **渠道是独立于卡的第二个变量，其量级与费率相当**：支付宝/微信对境外卡单笔 > CNY 200 收 3% 平台服务费（≤200 元免收），叠加美国卡的 3% FTF，可让一笔消费从 +1.5% 变成 −4.5%。**「刷哪张卡」和「走哪个渠道」必须一起算，不能拆成两个问题。**
3. **门槛与场景限定会静默放大误差**：澳门卡「3%」需当月累计 MOP15,000 才触发，且明确排除线上餐饮；美国卡季度轮换类别的 5x 只在当季有效。若产品不建模这两类约束，会把「1.5%」当「3%」推给用户，用户照做后感觉「这工具不准」。

> **由此定义产品的核心交付物不是「推荐一张卡」，而是「一张扣完所有成本的可比净回报率排名」。** 净回报率 = (返现 + 积分折算价值 − 外币手续费 − 渠道服务费) ÷ 消费金额。这一个公式就是本产品的全部护城河。

### 4.4 三地卡规则的关键差异，及对建模的影响

| 维度 | 美国发卡 | 香港发卡 | 澳门发卡 | **对产品建模的硬性影响** |
|---|---|---|---|---|
| **主计量单位** | 现金返还 %（少数为 x 倍数） | **每 HK$ X = 1 里数**（里数体系） | 现金返还 %（签账额回赠） | 必须引入「单位归一化层」：百分数直用；「x 倍数」需乘「每点估值」；「每元 1 里」需乘「每里估值」。**三种单位必须能换算为同一标量才能排序（见 Q1）** |
| **外币手续费 FTF** | 分化极明显：返现卡普遍 3%，旅行卡普遍 0% | 多数卡 0%–1%（视卡而定） | 通常 0%（本地发卡、本地结算） | FTF 必须是**每卡必填字段**，且默认值随发卡地区自动带出。漏填或默认 0 会让排名完全失真（最高频错误来源） |
| **奖励触发结构** | ①静态类别返现 ②**季度/月度轮换类别**（需激活） ③商户联名 offer | ①类别倍数（本地/海外/餐饮/网购分别计价） ②**月签总额门槛决定费率档位** ③需登记才生效 | ①**月度累计消费门槛**（如达 MOP15,000 才自 1.5% 升至 3%） ②指定日期（如逢周五）专属加码 ③明确排除线上、宴会、赌场、缴费等 | 需要支持三类约束：**上限（cap）**、**门槛（threshold）**、**渠道/场景适用性（applicability）**。三者任一缺失即产生静默错误。**MVP 必须支持「上限」与「门槛」两个字段的填写与计算，P1 才支持自动化的季度轮换与活动叠加** |
| **渠道适用性** | Apple Pay 通常不改变返现；绑定第三方平台可能触发 FTF | 部分卡对移动支付有独立加码 | 条款常明确排除线上交易、俱乐部会所内食肆等 | 「渠道」是独立维度，不能折叠进「卡」。**渠道差异必须建模为「卡 × 渠道」的费率修正，而非全局费率** |
| **数据可得性** | 高（英文结构化数据源多） | 中（比较平台聚合，但均为导流导向） | **低**（中文 PDF 年度条款，无结构化数据源） | **不能假设有可自动同步的卡库。前端必须把「手动录入 + 模板带出 + 编辑」当成一等公民功能，而不是兜底方案。** |
| **规则生命周期** | 季度/月度 | 季度/年度 | **年度推广期，每年重发条款** | 需要「上次确认日期」与新鲜度提示，见死因二。 |

**一句话总结对建模的影响**：**产品必须建立一个「卡 → 类别 → 渠道 → 上限/门槛 → 手续费」的五维费率模型，并输出单一可比的净回报率标量。** 这是数据模型的核心工作量所在，也是架构师最需要关注的部分（见 §13 Q2、Q3）。

## 5. 我们的差异化

> **同类工具回答「你应该办哪张卡」，我们回答「这一笔该刷哪张卡、走哪个渠道」。**

四条具体差异，每条都对应 §4 中的一个死因或空白：

| # | 差异点 | 对应解决的死因 / 空白 | 竞品为什么不做 |
|---|---|---|---|
| D1 | **净回报率比较：把 FTF 与渠道服务费作为一等公民从毛返现中扣除** | 填补「三地卡混持」空白；§4.3 证明这是收益差异最大的一项 | CardPointers/MaxRewards 是美国卡中心产品，FTF 在其语境里是「旅行时的注意事项」而非「日常消费的常态成本」；MoneyHero 只做申请比较 |
| D2 | **「卡 × 渠道」二维建模** | 支付宝/微信对境外卡的 3% 平台费使渠道成为与卡同量级的变量 | 竞品所在市场不使用支付宝/微信作为境外卡支付渠道，无此建模需求 |
| D3 | **明确承认数据新鲜度、显示「上次确认日期」，而非假装实时** | 死因二（静默失败） | 竞品的品牌叙事建立在「我们数据是最全最新的」，承认不确定会削弱其售卖理由；单人自用产品没有这个包袱 |
| D4 | **零授权、零登录、零绑定；数据 100% 在用户本地** | 死因三（授权过重导致放弃） | 竞品以订阅制变现，必须掌握用户账户与用量数据；本产品无变现目标 |

### 7.2 MVP 边界（严格）

**MVP = F1 + F2 + F3 + F4 + F5 + F6 + F7，共 7 个功能，全部 P0。**

判断依据：这 7 项中任缺一项，产品的**推荐结果就会错**或**用户拿不到结果**。

- 缺 F1 → 不是决策工具
- 缺 F2 → 无数据
- 缺 F3 → 拿不到结果，或慢到不可用
- 缺 F4 → 推荐错误时用户无法发现，也无法信任
- 缺 F5 → 把门槛/上限算错，产生静默错误（§4.1 死因二）
- 缺 F6 → 数据腐烂后仍自信推荐，信任一次性崩塌
- 缺 F7 → 录入成本白白付出（用户会放弃继续用）

**F8 / F9 / F10 全部进 Backlog，不进 MVP。** 具体理由：

- F8 活动叠加：Phase 0 虽列了「简单活动叠加」，但活动是**波动的、时效性强的、用户也记不住自己要手动维护的**数据源；MVP 缺它不影响主链路正确性（只是少算了额外奖励，属于「低估而非算错」）。等用户实际提出「某活动期间推荐不准」再上。
- F9 已用额录入：MVP 用「上限/门槛字段直接用默认计数 0（即视为未达门槛、未达上限）」可跑通主流程；用户若本月已刷很多，结果会偏保守（低估返现），不会算错方向。属可接受的降级。
- F10 消费地切换：MVP 用「币种选择」即可近似覆盖（澳门 → MOP，内地 → CNY），消费地本身不进入 MVP（见 §9 与 §13 Q5）。

## 8. P0 功能验收标准（EARS 格式）

> 格式：`While / When / If + 系统 + 必须/应该 + 行为`。每条均可被 QA 直接转成测试用例。术语：**净回报率** = (返现额 + 积分折算价值 − 外币手续费 − 渠道服务费) ÷ 消费金额。

### F1 净回报率比较引擎

- **F1-AC1** When 用户提供了金额、消费类别、支付渠道且卡库中至少有一张启用卡，系统**必须**对每张启用卡计算净回报率并输出一个按净回报率降序排列的列表，列表首项即为推荐卡。
- **F1-AC2** While 计算任一卡的净回报率，系统**必须**按 `净额 = 返现额 + 积分折算价值 − (金额 × 该卡外币手续费率) − (金额 × 渠道服务费率)` 计算，且**必须**将外币手续费与渠道服务费作为扣减项参与排序，不得仅在展示层提示。
- **F1-AC3** If 某卡计算出的净回报率为负，系统**必须**以原始负值展示该卡的净回报率与净额，不得截断为 0、不得从列表中隐藏。
- **F1-AC4** If 排名第一与第二的卡净回报率差值小于 0.1 个百分点，系统**必须**在两行上同时标记「基本持平」状态标识。
- **F1-AC5** When 用户修改任一卡的费率字段并保存，系统**必须**在 300ms 内用新规则重算当前结果列表，无需用户手动触发刷新。
- **F1-AC6** While 卡库中启用的卡数量为 0，系统**必须**展示空状态引导，引导内容为「添加第一张卡」，不得展示空白结果区或报错。

### F2 卡库管理与模板

- **F2-AC1** When 用户从模板列表中选择一个模板，系统**必须**将模板的返现规则预填到一个可编辑表单中，且用户**必须**能够修改其中任意字段后再保存（预填不得为只读）。
- **F2-AC2** While 用户创建或编辑一张卡，系统**必须**要求「外币手续费率」字段有值；If 该字段为空，系统**必须**阻止保存并给出字段级错误提示。
- **F2-AC3** When 用户新建一张卡且未手动填写外币手续费率，系统**必须**按 `发卡地区 + 卡组织` 二维自动带出默认值，且该默认值**必须**可被用户覆盖。
  - 中国香港发卡：Visa / Mastercard = **1.95%**，银联双币 = **0%**（人民币/澳门币场景）/ 1%（其他外币），Amex = **2.0%**，AEON = 1.5%
  - 美国发卡：默认 **3%**（旅行类卡可达 0%，由模板带出）
  - 中国澳门发卡：Visa / Mastercard = **1.95%**（部分银行 1.75%），银联全币种卡 = **0%**（优惠期内）
  - 依据：`docs/ARCHITECTURE.md` §3.5，逐条带官方来源 URL 与核实日期（2026-10-31）
- **F2-AC4** While 用户填写香港发卡类卡的里数型返现，系统**必须**同时展示原始单位（如「每 HK$ 4 = 1 里」）与折算后的等效返现率，且用户修改原始单位或里数估值时折算值**必须**同步更新。
- **F2-AC5** When 用户删除一张卡，系统**必须**二次确认，确认后**必须**执行软删除（该卡不再参与比较，但记录保留，可恢复）。
- **F2-AC6** If 用户在模板选择界面的搜索框中输入关键词，系统**必须**对模板卡名做包含匹配并实时过滤列表。
- **F2-AC7** If 用户输入的模板搜索关键词无任何匹配结果，系统**必须**展示「没有找到，手动创建空白卡」的可点击入口，而非空白列表。

### F3 付款前快速测算主界面

- **F3-AC1** When 用户在主界面输入合法金额并已选择消费类别与支付渠道，系统**必须**在输入变化后 200ms 内更新结果列表，且**不得**要求用户点击「计算」按钮。
- **F3-AC2** While 用户打开主界面，系统**必须**自动聚焦金额输入框并唤起数字键盘。
- **F3-AC3** When 用户完成一次测算并离开，系统**必须**记住本次选择的消费类别与支付渠道，下次打开时**应该**默认选中上次的值。
- **F3-AC4** If 用户输入金额为空、为 0、为负数或非数字，系统**必须**不展示结果列表，并展示中性提示（如「输入金额即可看到推荐」），不得报错、不得展示 0 元排名。
- **F3-AC5** While 用户在主界面，系统**必须**提供消费类别选项恰好为 7 项（餐饮 / 超市 / 加油 / 机票 / 酒店 / 网购 / 其他）与支付渠道选项恰好为 5 项（刷卡 / 支付宝 / 微信 / 云闪付 / Apple Pay）。
- **F3-AC6** When 用户在主界面切换支付渠道，系统**必须**重新计算全部卡的净回报率，而非仅对当前推荐卡做修正。

### F4 算式展开（可解释性）

- **F4-AC1** When 用户点击任一结果行的「为什么」入口，系统**必须**展开该卡的算式分解，**必须**至少包含四项：毛返现（含积分折算价值的来源说明）、外币手续费扣减额、渠道服务费扣减额、净额。
- **F4-AC2** While 展示某卡的算式分解，系统**必须**标明该卡当前实际适用的返现率与其来源（如「餐饮 3%（已达月签门槛）」或「餐饮 1.5%（未达月签 MOP15,000 门槛，按基础档计）」）。
- **F4-AC3** If 某卡因达到上限而被封顶，算式分解的顶部**必须**优先展示封顶提示及该上限的当前状态，且展示的返现额**必须**为封顶后的金额。
- **F4-AC4** While 算式抽屉展开，系统**必须**提供关闭按钮，且点击抽屉外部遮罩区域**必须**同样关闭抽屉。

### F5 上限与门槛建模

- **F5-AC1** If 某卡某类别配置了月度或季度返现上限且该上限已被用尽，系统**必须**按该卡的基础（非加码）返现率计算该类别的返现额，而非按加码率计算。
- **F5-AC2** If 某卡配置了月度累计消费门槛，且系统当前记录的本月累计消费未达该门槛，系统**必须**按门槛未达成的费率档计算该卡的返现额。
- **F5-AC3** When 用户为某卡填写了月度累计消费金额且该金额已达到或超过门槛值，系统**必须**按门槛达成后的费率档计算。
- **F5-AC4** While 计算涉及门槛或上限，系统**必须**在 F4 的算式分解中显式展示「未达门槛 / 已达门槛 / 已达上限」中的当前状态。
- **F5-AC5** If 门槛或上限字段为空，系统**必须**按「无该约束」处理（即不封顶、按最高费率档计算），不得将空值视为 0。

### F6 数据新鲜度标记

- **F6-AC1** While 用户查看卡库列表，系统**必须**为每张卡展示「上次确认日期」。
- **F6-AC2** When 用户编辑并保存任一卡的规则，系统**必须**将该卡的「上次确认日期」更新为保存当日。
- **F6-AC3** If 某卡的「上次确认日期」距今超过 90 天，且该卡出现在结果列表中，系统**必须**在该行上展示「规则可能已变，请确认」的提示标识。
- **F6-AC4** If 推荐卡（列表首个）的「上次确认日期」距今超过 90 天，系统**必须**在冠军卡区域同位置展示上述提示，且该提示**不得**遮挡净回报率数值。
- **F6-AC5** While 用户查看某卡详情，系统**必须**提供「标记为已确认」操作，触发后将该卡的上次确认日期更新为当日。

### F7 本地持久化与导出导入

- **F7-AC1** When 用户关闭并重新打开应用，系统**必须**完整恢复卡库与最近一次测算选择的类别/渠道，不得要求重新录入。
- **F7-AC2** When 用户触发导出，系统**必须**生成一个包含全部卡规则与设置的文件供下载。
- **F7-AC3** When 用户导入一个由本产品导出的文件，系统**必须**校验文件结构，若结构合法则恢复卡库并提示导入成功的卡数量。
- **F7-AC4** If 导入的文件结构不合法（缺少必需字段或格式错误），系统**必须**拒绝导入、保留现有卡库不被破坏，并给出明确的失败原因（不得静默失败）。
- **F7-AC5** If 导入的卡库与现有卡库存在同名卡，系统**必须**在导入前提示冲突并让用户选择「覆盖 / 保留两者 / 取消」，不得自动静默覆盖。

## 9. 明确不做什么（Out-of-Scope）+ 原因

> 依据 `spec-as-contract.md` §2 与 §3：不写清楚不做什么，执行者就会顺手加上未被要求的特性。以下每一条都是**明令禁止**在 MVP 中出现的。

| # | 不做的事 | 原因 |
|---|---|---|
| O1 | **注册、登录、账号体系、密码、验证码** | 单人自用；任何账号环节都增加一次前置操作，与「用得爽 / 3 秒出结果」直接冲突。无账号 = 无用户资产需保护（§4.1 死因三） |
| O2 | **绑定银行账户、网银授权、短信验证、邮箱账单解析、自动导入消费流水** | 这是 MaxRewards 的死因复刻：授权引发不适 → 解绑 → 工具失效 → 卸载。且本产品不需要它就能算对（§4.2） |
| O3 | **汇率成本建模、实时汇率、DCC（动态货币转换）判断** | Phase 0 已锁定不做。补充理由：实时汇率引入外部依赖与失败面，而其误差量级远小于 FTF 与渠道费；DCC 属于「付款动作现场决策」，不是「选卡决策」（作为已知风险写入 §13 Q6，不实现） |
| O4 | **账单管理、还款日提醒、免息期计算、授信额度管理** | 云闪付已免费且更好；与本产品决策点零交集，属「看起来有用实际不用」（§4.2） |
| O5 | **开卡奖励（SUB）追踪、该申请哪张卡、产品推荐** | 用户已持卡；申请决策与付款决策是两个不同时点。这是 MoneyHero/MaxRewards 的战场，不是我们的 |
| O6 | **里程/积分余额追踪、机票兑换搜索、里数转点** | PointsYeah 专精且更强；本产品只需「每里估值」一个标量输入即可完成比较（§4.4 单位归一化） |
| O7 | **多用户、家庭成员、多人共享、权限角色** | Phase 0 已锁定：仅个人自用 |
| O8 | **社交分享、邀请、推荐好友、公开榜单** | 无增长目标；且真实持卡规则是敏感信息 |
| O9 | **卡面图片管理、主题换肤、多套配色、动画特效堆叠** | 「用得爽」指决策速度，不是视觉表演。视觉**质量**仍须达标（由设计师按行业规范产出），但不做「主题系统」这类功能 |
| O10 | **AI 拍照识别小票、OCR、语音输入、自然语言问答式录入** | 与本产品决策点无关；引入识别失败分支，稀释 3 秒指标；且单人自用下语音/文字录入的边际收益远低于其失败成本 |
| O11 | **消费分类报表、饼图、月度支出分析、预算管理** | 属于记账工具能力；用户没提出，且不改变「这笔刷哪张」（§4.2） |
| O12 | **云端同步、多设备实时同步、协作** | 单人 1–2 台设备，F7 的本地存储 + 导出导入已覆盖；云端同步需要后端与账号，违反 O1 |
| O13 | **自动抓取/爬取银行条款更新** | 澳门发卡规则为中文年度 PDF，无稳定结构化数据源，自动抓取会产生**静默错误**（比"不更新"更危险）。改为 F6 的新鲜度标记 —— 承认不确定 |
| O14 | **在 MVP 中实现活动叠加（F8）、已用额录入（F9）、消费地切换（F10）** | 均属「缺少时低估而非算错」，可降级运行。进 Backlog，由用户真实痛点驱动（§7.2） |
| O15 | **多语言 / i18n** | 唯一用户为中文使用者；投入产出为零 |
| O16 | **暗色模式** | 不影响决策结果。若设计师在视觉阶段顺手带上可接受，但**不得**作为 MVP 验收项 |
| O17 | **批量导入预置大卡库（几百张卡）** | 用户只需自己的 10–20 张；预置过多会让模板列表变成「搜索大海」，增加选择成本。模板数量以「覆盖三地最常见卡种」为限，具体清单由 PM 与架构师在 Phase 1 技术评审中确认（§13 Q7） |

## 10. 关键产品决策与理由

| # | 决策 | 理由 | 被否决的替代方案 |
|---|---|---|---|
| D-01 | **排名主指标用「净回报率（%）」而非「净赚金额」** | 百分比可跨金额横向比较，也与用户心智中的「3% 返现」同语言；净额作为副信息展示 | 只用净额排序 → 大额消费时金额差异掩盖费率差异，且无法解释「为什么这张更好」 |
| D-02 | **输入即算，无「计算」按钮** | 少一次点击 = 少一次放弃机会；「3 秒出结果」的第一性要求 | 「填完表单点计算」→ 传统表单心智，反「用得爽」 |
| D-03 | **FTF 与渠道服务费作为扣减项进入排序本体，而非提示文案** | 这是产品唯一护城河（§4.3）；若只做提示，产品退化为「带提醒的卡列表」 | 「排名按毛返现，另加一行小字提示 FTF」→ 用户仍会选错，且丧失了相对竞品的差异 |
| D-04 | **负数净回报必须显式展示** | 用户需要知道「这笔不该刷这张」。隐藏负数即等于骗用户去亏钱 | 「只显示正收益的卡」→ 用户以为所有卡都是正收益 |
| D-05 | **差额 < 0.1pp 标记「基本持平」，不给单一答案** | 数据本身有精度限制（里数估值本身是区间）；假装精确是产品诚信问题 | 「永远给出唯一冠军」→ 用户照做后发现无差异，信任下降 |
| D-06 | **不建官方大卡库，只做模板 + 用户自助** | 三地（尤其澳门）无可维护的结构化数据源；单人自用下用户本人即最优数据源（§4.1 死因一） | 「我们维护三地全卡库」→ 一个人的团队必然腐烂，且腐烂后产生静默错误 |
| D-07 | **用「上次确认日期 + 90 天过期提示」代替自动更新** | 承认数据不新鲜比假装新鲜更能维持长期信任（§4.1 死因二） | 「自动抓取条款」→ O13，产生静默错误 |
| D-08 | **数据存本地 + JSON 导出导入，不做云端** | 无账号=无授权摩擦、无后端、无隐私责任；导出导入已足够覆盖换机场景 | 「云端同步」→ 违反 O1/O12，成本与风险远超收益 |
| D-09 | **卡删除做软删除** | 用户可能只是暂时停用某卡（如剪卡后又重办）；误删的恢复成本远高于存储成本 | 硬删除 → 一次误操作让用户重录规则，直接触发放弃 |
| D-10 | **空/未填的门槛与上限视为「无约束」而非 0** | 空值是「用户不知道」，0 是「用户知道是 0」；按 0 处理会导致所有卡返现被算成 0，产品直接失效 | 空值按 0 处理 → 灾难性错误 |
| D-11 | **渠道作为与卡独立的第二维度** | 支付宝/微信对境外卡 3% 平台费与 FTF 同量级（§4.3 第二行组）；折叠进卡会算错 | 「渠道只是备注字段」→ 无法回答「同卡换渠道差多少」，而这正是最高价值洞察 |
| D-12 | **MVP 不做活动叠加** | 活动数据波动大、用户自身也难维护；缺失仅导致低估，不导致算错 | 「MVP 就上活动」→ 引入最易腐烂的数据源，拉长交付周期 |

## 11. 非功能需求

| 类别 | 要求 | 优先级 |
|---|---|---|
| 性能 | 首屏可交互 < 1.5s；输入到结果更新 < 200ms（F3-AC1）；卡库页面 20 张卡渲染 < 300ms | P0 |

## 12. 风险与开放问题

### 12.1 产品风险（按严重度）

| # | 风险 | 严重度 | 说明 | 缓解动作 |
|---|---|---|---|---|
| R1 | **数据腐烂导致静默错误，信任一次性崩塌** | **最高** | 三地规则（尤其澳门年度推广条款、香港月签门槛、美国季度轮换）变动频繁且无通知。产品会自信地给出过期推荐。这是所有同类工具的共同死因，也是本产品最可能失败的方式 | ①F6 新鲜度标记（MVP 低保真缓解）②UI 上永久展示「以你的卡条款为准」的定位声明，不承诺权威性 ③结果区提供「这张卡我确认过了」的一键确认，把维护成本压到 1 秒 ④**接受「不完美」并写进产品语言，而不是隐瞒** |
| R2 | **录入成本过高，用户在 Onboarding 阶段放弃** | **高** | 10–20 张卡 × 每张 8–12 个字段。若首次录入体验笨重（如逐字段填、无模板、字段含义不清），用户在看到第一个结果前就已流失——产品在其核心价值兑现前即死亡 | ①模板一键带出 + 全部字段可改（F2-AC1）②默认值按发卡地区自动带出，尤其 FTF（F2-AC3）③允许「先试用示例卡」看到价值，再回来录入 ④Onboarding 可分多次完成，随时退出不丢数据（§2.1 坑 1）⑤**录入环节允许脏数据**：先粗填能用，后续再精修 |
| R3 | 里数估值主观化，导致香港卡排名不可信 | 中 | 「1 里值多少钱」因人而异（换经济舱 vs 商务舱差异极大），且产品不建模兑换场景 | 里数估值作为**显式可调参数**并默认给出保守值；在算式展开中标明「按你设定的每里 X 元折算」（F4-AC1） |
| R4 | 三地币种混算导致用户误读 | 中 | 澳门卡结算 MOP、香港卡结算 HKD、美国卡结算 USD，用户在澳门刷 MOP 时看到的「净赚」是哪种币？若含糊，用户会认为算错 | MVP 强制以「用户输入的消费币种」为展示币种（不换算，因 Phase 0 已锁不建模汇率），并在结果区显著标注币种 |
| R5 | 渠道建模粒度不足导致「Apple Pay 走支付宝」这类嵌套场景算错 | 中 | 用户可能用 Apple Pay 绑定的卡在支付宝内付款；MVP 的 5 渠道是互斥单选，无法表达嵌套 | MVP 明确 5 渠道互斥（F3-AC5），并在渠道选择处标注适用范围；嵌套场景写入 §13 Q5，不实现 |

| # | 问题 | 影响面 | 建议 | 责任方 |

## 13. 端到端验证步骤（收尾即验收，可执行）

> 依据 `spec-as-contract.md` §4：验证必须可执行、覆盖核心成功流 + 关键错误/边界流。

### 13.1 核心成功流（必须全部通过才算 MVP 可用）

**步骤 E1｜建库：模板一键带出**
1. 打开应用 → 确认落地屏直接为「算一笔」主界面，**无**欢迎页、**无**登录、**无**引导轮播（验证 O1）。
2. 点「添加我的第一张卡」→ 在模板搜索框输入「Gold」→ 确认列表实时过滤且出现含「Gold」的模板。
3. 选中该模板 → 确认进入的规则表单**已预填**发卡地区、结算币种、外币手续费率（值应为 3%，验证 F2-AC3）、7 类别费率。
4. 清空「外币手续费率」→ 点保存 → **断言：保存被阻止，且错误提示指向该字段**（验证 F2-AC2）。
5. 重新填入 0 → 保存 → **断言：卡出现在卡库中，上次确认日期 = 今日**（验证 F6-AC2）。

**步骤 E2｜建库：香港里数卡的单位归一化**
6. 再添加一张香港发卡里数卡模板 → **断言：表单同时显示「每 HK$ 4 = 1 里」与折算后的等效返现率**（验证 F2-AC4）。
7. 将里数估值参数由默认值修改 → **断言：等效返现率同步变化**（验证 F2-AC4）。

**步骤 E3｜主链路：3 秒出结果**
8. 回到主界面 → **断言：金额输入框已自动聚焦**（验证 F3-AC2）。
9. 输入 `1000` → 点「餐饮」→ 点「刷卡」→ **断言：结果列表在 200ms 内出现，无「计算」按钮被点击**（验证 F3-AC1、D-02）。
10. **断言：列表按净回报率降序，首行为冠军卡，且显示净回报率与前若干位的净额。**

**步骤 E4｜核心价值：FTF 是否被正确吃掉返现**
11. 造两张卡：卡 A「餐饮 3%，FTF 0%」、卡 B「餐饮 3%，FTF 3%」，其余相同，金额 1000。
12. **断言：卡 A 净回报率 = 3.00%，卡 B 净回报率 = 0.00%，且 B 排在 A 之后**（验证 F1-AC2，复现 §4.3 第 4 行结论）。
13. 再加卡 C「餐饮 1.5%，FTF 3%」→ **断言：卡 C 净回报率 = −1.50% 且以负数红色显示于列表最后，未被隐藏或被截断为 0**（验证 F1-AC3、F4）。

**步骤 E5｜核心价值：渠道差异**
14. 保持金额 1000、类别餐饮，将渠道由「刷卡」切为「支付宝」→ **断言：全部卡的净回报率被重新计算（而非仅冠军卡）**（验证 F3-AC6）。
15. 对一张 FTF 0%、餐饮 4x（点值折算 6%）的卡：刷卡时应为 6.00%，支付宝渠道（平台费 3%）时应为 3.00%（复现 §4.3 第 6 行）。**断言：两者差值为 3.00 个百分点。**

**步骤 E6｜可解释性**
16. 点任一行的「为什么」→ **断言：抽屉展开并列出毛返现、外币手续费扣减、渠道服务费扣减、净额四项**（验证 F4-AC1）。
17. **断言：抽屉标明该卡实际适用的返现率及来源**（验证 F4-AC2）。
18. 点遮罩关闭 → **断言：抽屉关闭**（验证 F4-AC4）。

**步骤 E7｜上限与门槛**
19. 给某卡设置「月度餐饮返现上限 = MOP 30」并将本月已用额置为 30（若 F9 未上线则用测试注入）→ **断言：该卡返现额按基础费率计算，且抽屉顶部显示封顶提示**（验证 F5-AC1、F5-AC3、F4-AC3）。
20. 给某卡设置「月签门槛 MOP15,000」且本月累计填 10,000 → **断言：按门槛未达档（1.5%）计算，抽屉显示「未达门槛」**；改为 16,000 → **断言：按 3% 计算**（验证 F5-AC2、F5-AC3、F5-AC4）。
21. 清空门槛字段 → **断言：按「无约束」处理，不按 0 处理**（验证 F5-AC5、D-10）。

**步骤 E8｜边界与空状态**
22. 清空金额 → **断言：结果列表消失，出现中性提示，无报错**（验证 F3-AC4）。
23. 输入 `0`、`-100`、`abc` → **断言：同上，均不展示排名**（验证 F3-AC4）。
24. 停用全部卡 → **断言：出现「添加第一张卡」空状态引导，非空白结果区**（验证 F1-AC6）。

**步骤 E9｜持久化**
25. 刷新页面 → **断言：卡库完整恢复，且类别/渠道记住上次选择**（验证 F7-AC1、F3-AC3）。
26. 导出 → 清空本地数据 → 导入该文件 → **断言：卡库恢复且提示导入数量**（验证 F7-AC2、F7-AC3）。
27. 导入一个被破坏的 JSON（删掉一个必需字段）→ **断言：拒绝导入、现有卡库未被破坏、给出明确失败原因**（验证 F7-AC4）。
28. 导入含同名卡的库 → **断言：出现冲突提示并让用户三选一，未静默覆盖**（验证 F7-AC5）。

**步骤 E10｜数据新鲜度**
29. 将某卡上次确认日期改为 100 天前 → **断言：该卡行出现「规则可能已变，请确认」**（验证 F6-AC3）；若该卡为冠军卡，提示不得遮挡净回报率数值（验证 F6-AC4）。
30. 点「标记为已确认」→ **断言：该卡日期更新为今日，提示消失**（验证 F6-AC5）。

**步骤 E11｜P0 绝对规则合规检查（逐条肉眼验证）**
31. **断言：全站无任何 emoji 充当功能图标**（搜索源码确认无 emoji 字符用于图标位；图标均为 SVG）。
32. **断言：全站无紫色→粉色渐变**。
33. **断言：无 "Welcome to" / "Lorem ipsum" / "Sign up today" / "Get Started" 类空文案**；空状态与错误态文案均为具体行为指引。

### 13.2 完成定义（Definition of Done）

MVP 交付完成 = E1–E11 全部断言通过 + §7.1 全部 P0 功能的 EARS 验收标准逐条可追溯 + 无 P0 级回归缺陷。

### 13.3 回归衔接

E4、E5、E7 三项是**本产品的价值支点**，必须沉淀为长期回归用例：任何改动导致「卡 A 3%/0% FTF 与卡 B 3%/3% FTF 的净回报率差不再为 3.00pp」，或「负净回报被隐藏」，或「门槛/上限不再影响计算」，即视为破坏产品核心，必须打回。

### 14.2 关键数据换算口径（供架构师实现时对齐）

- **美国卡「4x」换算**：按 1 点 = 1.5 美分估值（AmEx MR 常用保守口径）→ 4x ≈ 6% 等效返现。架构师须将「点值」做成可调全局参数，不得硬编码。
- **香港卡「HK$4 = 1 里」换算**：按 1 里 ≈ HK$0.08 估值 → 每 HK$1 得 0.25 里 × 0.08 = 2% 等效返现。**里数估值必须作为显式参数暴露给用户**（见 R3、Q1）。
- **支付宝/微信渠道费**：单笔 ≤ CNY 200 → 0%；> CNY 200 → 3%。**MVP 若无法判断单笔阈值，必须按「全额 3%」保守计算**，不得静默按 0 处理（否则产生乐观偏差，与「宁可低估」原则矛盾）。
- **澳门卡门槛**：MOP15,000 为「当月本地及/或海外零售签账累计」，不含积分兑换、现金透支、年费、手续费、网上缴费、缴税、赌场等。MVP 只需支持「一个门槛值 + 未达/已达两档费率」，不需要建模「哪些交易计入门槛」。
- **展示币种**：统一以用户输入的消费币种展示，不做跨币换算（Phase 0 已锁：不建模汇率）。
